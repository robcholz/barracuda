## Overview

Barracuda separates semantic peripheral APIs, peripheral implementations, and
low-level chip drivers. A Board has exactly two public hardware surfaces:
`peripherals` and `exposed-io`. Everything used only to construct a peripheral,
including GPIO expanders and bus switches, remains private to its implementation.

Composition happens at build time. The selected Board HAL contains concrete
types and `Option<T>` fields; firmware performs no runtime catalog lookup and
uses no peripheral trait objects.

## Ownership boundaries

- `peripherals/api` defines chip-independent semantic contracts such as
  `Display`, `Touch`, `PowerMonitor`, and `RealTimeClock`, plus the common
  `PeripheralImplementation` construction trait.
- `peripherals/impl/<peripheral>/<implementation-id>` adapts one concrete
  hardware arrangement to one semantic API. It owns its `peripheral.yml`,
  initialization policy, and private helper-chip dependencies.
- `peripherals/config` discovers only peripheral implementations, validates
  their manifests and Board wiring, and generates static Board composition.
- `drivers/chips/<chip>` contains low-level register and protocol drivers.
  Chip drivers know neither Board names nor semantic peripheral APIs and have
  no `peripheral.yml`.
- `boards/hal` owns the `BoardResources { peripherals, exposed_io }` envelope
  and the resource adapters used by generated composition.

The dependency direction is one-way:

~~~text
Platform HAL resource -> chip driver -> peripheral implementation -> peripheral API
                                  Board wiring -----------^
~~~

A peripheral implementation may use no separate chip crate when an upstream
ecosystem crate already provides the low-level driver. The semantic boundary is
still the same: System receives only the peripheral API.

## Board model

`board.yml` names product wiring, not Rust modules:

~~~yaml
peripherals:
  io:
    i2c-device:
      internal:
        peripheral: I2C0
        scl: GPIO32
        sda: GPIO31
        frequency-hz: 400000
  devices:
    battery-monitor:
      implementation: ina226-power-monitor
      bindings:
        i2c: internal
      parameters:
        address: 65

exposed-io:
  pins:
    port-a-sda: { pin: GPIO53 }
~~~

`peripherals.io` declares private resources consumed during construction.
`peripherals.devices` selects semantic implementations. `exposed-io` is the
only runtime-configurable Board I/O surface. A chip-native token cannot be both
private peripheral wiring and exposed I/O.

Some panels answer reads on the same line the host writes on. Such an
`spi-device` names that line as `mosi` and sets `three-wire: true`; its reads
then come back on `mosi`, at `read-frequency-hz` when the device answers only
at a slower clock than it is written:

~~~yaml
spi-device:
  display-spi:
    peripheral: SPI3
    sck: GPIO17
    mosi: GPIO21
    three-wire: true
    read-frequency-hz: 8000000
    chip-select: GPIO15
    frequency-hz: 40000000
~~~

A line an implementation drives at one moment and reads at another is a `gpio`
binding: the Board names its pin, and the implementation receives a
`ConfigurableDigitalPin` it switches between output and input. The Tab5
display drives the touch interrupt line high while the touch controller leaves
reset, which straps the GT911 address, and then releases it to the controller.
An input whose bias the implementation sets is a `gpio` binding as well:
`gpio-buttons` makes each button pin an input with the pull the Board names.
An optional `gpio` or `digital-input` binding the Board leaves out reaches the
implementation as `None`.

A panel on an eight-bit Intel 8080 bus is a `parallel-output`: its write
strobe, data/command and chip-select lines, eight data lines in bit order, the
strobe clock, and the DMA staging buffer, whose size is the longest burst sent
under one chip-select assertion. The Platform hands it to the display
implementation as a `ParallelOutput`:

~~~yaml
parallel-output:
  display-bus:
    peripheral: LCD_CAM
    dma: DMA_CH1
    wr: GPIO11
    dc: GPIO12
    chip-select: GPIO14
    data: [GPIO13, GPIO9, GPIO8, GPIO7, GPIO6, GPIO5, GPIO4, GPIO3]
    frequency-hz: 10000000
    dma-buffer-bytes: 4096
~~~

A directly driven e-paper panel's source driver uses the same binding without
`dc`: every byte is data, its source clock is `wr`, and its source start pulse
is `chip-select`. Its display implementation drives the gate and latch lines
as ordinary digital outputs and keeps each line within one burst.

A parallel camera sensor is a `camera-capture`: the camera controller and
its DMA channel, the pixel clock, VSYNC, HREF, eight data lines in bit order,
the master clock and its frequency, and the DMA storage for one frame. The
Platform hands it to the camera implementation as a `FrameReceiver`, which
receives one whole frame per call. A sensor module with its own oscillator
takes no master clock: the Board leaves out `xclk` and `xclk-frequency-hz`.
The M5Stack CoreS3's GC0308, one 320x240 RGB565 frame:

~~~yaml
camera-capture:
  camera-data:
    peripheral: LCD_CAM
    dma: DMA_CH0
    pclk: GPIO45
    vsync: GPIO46
    href: GPIO38
    data: [GPIO39, GPIO40, GPIO41, GPIO42, GPIO15, GPIO16, GPIO48, GPIO47]
    dma-buffer-bytes: 153600
~~~

A microSD card is an `sdmmc-device`: the SD host, the `slot` of it the card
is wired to (0 when left out), the clock, command and data pins in order, the
`bus-width` (1 or 4), the clock the card runs at once identified
(`frequency-hz`, 25 MHz when left out), and, when the chip powers the slot's
pads from an on-chip regulator, that regulator's `power-channel` and
`power-millivolts`. Each Platform lists the SD host slots it hands to a Board
and the supply each needs (`hal.sdmmc-slots` in `platform.yml`), and
`cargo board select` refuses a card on another slot, with another supply, or
on the slot a Wi-Fi co-processor uses. The ESP32-P4's card:

~~~yaml
sdmmc-device:
  micro-sd:
    peripheral: SDHOST
    slot: 0
    clk: GPIO43
    cmd: GPIO44
    data: [GPIO39, GPIO40, GPIO41, GPIO42]
    bus-width: 4
    power-channel: 4
    power-millivolts: 3300
    frequency-hz: 40000000
~~~

The binding is the Platform's to build. On the ESP32-S3 the Board composition
takes the SD host and builds the card's slot. On the ESP32-P4 the Platform owns
the SD host, because the Wi-Fi co-processor's link uses its other slot: the
Platform entry builds the host once and hands slot 0 to the Board composition
beside the chip peripherals, and the card implementation receives that slot.

Several `spi-device` declarations may name one SPI controller when devices
share its bus, such as an LCD and a microSD card. They name the same `sck`,
`mosi`, and `miso`, and each its own `chip-select` and `frequency-hz`; the
composition builds the bus once and hands each implementation a device that
selects itself and applies its clock. The M5Stack Core2's display and card:

~~~yaml
spi-device:
  display-spi:
    peripheral: SPI3
    sck: GPIO18
    mosi: GPIO23
    miso: GPIO38
    chip-select: GPIO5
    frequency-hz: 40000000
  card-spi:
    peripheral: SPI3
    sck: GPIO18
    mosi: GPIO23
    miso: GPIO38
    chip-select: GPIO4
    frequency-hz: 20000000
~~~

A microSD card on SPI (`spi-sd-fat-removable-storage`) also changes its
device's clock and clocks it with the chip select released, which the SD
specification asks for while it identifies the card; the Platform's SPI device
types provide that through `SpiDeviceControl`.

An `spi-bus` is an SPI controller with no chip select: the implementation
drives its device's select line itself, as a `digital-output`. The ESP
Platforms' bus also implements `SpiBusControl`, which sets the clock and mode
and clocks out fewer than eight bits through the controller's command phase.
The ATOM Display's `m5hdmi-display` uses it to load its FPGA over JTAG on the
same four lines (TCK on SCK, TDI on MOSI, TDO on MISO, TMS on the select line)
before talking SPI to it:

~~~yaml
spi-bus:
  fpga-spi:
    peripheral: SPI3
    sck: GPIO5
    mosi: GPIO19
    miso: GPIO22
    frequency-hz: 40000000
~~~

An `spi-output`, the data line of an LED strip clocked out of an SPI
controller, takes a whole controller of its own: one that no `spi-device`
names. A Board therefore needs a free controller for each `spi-output` beside
the buses its `spi-device` entries use.

An `rmt-output` is one transmit channel of the remote-control transceiver
(the ESP RMT) and its pin, and an `rmt-input` one receive channel. Several
channels may name one transceiver: the composition builds it once and hands
each implementation its channel as a `PulseOutput` or `PulseInput`, which
clock out or record level-and-duration symbols on their own. An LED chain on
an `rmt-output` (`rmt-led-strip`) therefore takes no SPI controller, and an
infrared LED and receiver use the same channels' carrier and glitch filter.
Each Platform lists the channels that transmit and receive
(`hal.rmt-channels` in `platform.yml`), and `cargo board select` refuses a
channel outside them. The M5Stack StickS3's infrared transmitter and
receiver:

~~~yaml
rmt-output:
  ir-transmit:
    peripheral: RMT
    channel: 0
    pin: GPIO46
rmt-input:
  ir-receive:
    peripheral: RMT
    channel: 4
    pin: GPIO42
~~~

A `pwm-output` is one timer and one output channel of a PWM controller (the
ESP LEDC) and the pin they drive. The implementation retunes the timer,
through `PwmFrequencyControl`, so a passive buzzer changes pitch; the duty
cycle sets its volume. The controller is built once and shared: Board PWM
outputs and the runtime PWM pool each take their own timers and channels,
and `cargo board select` refuses an output that names one of the pool's. The
M5Stack Dial's buzzer:

~~~yaml
pwm-output:
  buzzer-tone:
    peripheral: LEDC
    timer: Timer1
    channel: Channel1
    pin: GPIO3
~~~

An `analog-input` is one ADC channel: the controller and the pin. Several
inputs may name one controller; the composition enables every channel, builds
the converter once, and hands each implementation its channel, which reads
calibrated millivolts (`AnalogVoltageInput`). The ESP32-S3-Korvo-2's button
ladder and battery:

~~~yaml
analog-input:
  button-ladder:
    peripheral: ADC1
    pin: GPIO5
  battery-sense:
    peripheral: ADC1
    pin: GPIO6
~~~

A `pulse-counter` is one pulse-counter unit that decodes a quadrature
encoder: the controller and the pins of its A and B signals, which the
Platform biases with their internal pull-ups. The unit counts every edge of
both signals, up while B leads A, and the Platform widens its sixteen-bit
count in software; the implementation receives a `QuadratureDecoder`. The
M5Stack Dial's knob:

~~~yaml
pulse-counter:
  knob:
    peripheral: PCNT
    a: GPIO41
    b: GPIO40
~~~

A `twai` is the chip's own classic CAN controller (the ESP TWAI) and the pins
of its transceiver: `tx` drives the transceiver's TXD input and `rx` reads its
RXD output. The transceiver needs no driver. The implementation receives a
`CanController`, which stays off the bus until the application chooses the
bit rate, so a Board never disturbs a bus whose rate it does not know. The
M5Stack StamPLC's CAN port:

~~~yaml
twai:
  can-bus:
    peripheral: TWAI0
    tx: GPIO42
    rx: GPIO43
~~~

A `pdm-i2s-stream` is a PDM microphone and an I2S amplifier on one I2S
controller, one direction at a time: `clk` is the microphone's clock and the
amplifier's word select, `din` the microphone's data, and `bclk` with `dout`
the amplifier's lines. A product with only one of them leaves the other's
lines out. The stream carries mono 16-bit PCM at `sample-rate-hz`; the
Platform sizes its DMA buffers with `dma-buffer-bytes`. The M5Stack Atom
Echo:

~~~yaml
pdm-i2s-stream:
  audio:
    peripheral: I2S0
    dma: DMA_I2S0
    clk: GPIO33
    din: GPIO23
    bclk: GPIO19
    dout: GPIO22
    sample-rate-hz: 16000
    dma-buffer-bytes: 4096
~~~

A Board may declare several devices of any kind except removable storage, and
marks exactly one of them `primary: true`: the product's main device of that
kind, such as the front display or the speaker's codec. A kind with one device
needs no mark. A product whose several chips make up one device presents them
through one implementation that composes their drivers: the M5Stack AirQ's
SEN55 particulate sensor and SCD40 CO2 sensor are one `environment-sensor`
device, `scd4x-sen5x-environment-sensor`, whose quantities are the union of
the two chips'.

~~~yaml
peripherals:
  devices:
    front-buttons:
      implementation: gpio-buttons
      primary: true
      bindings: { ... }
    side-buttons:
      implementation: gpio-buttons
      bindings: { ... }
~~~

A Board has at most one `removable-storage` device. System, not a Plugin,
takes it, without an instance, and mounts it at `/removable/<slot-id>` with one
lifecycle task; `cargo board select` rejects a second card.

Every generated semantic slot is optional. A Board with no real-time clock has
no `RealTimeClock` value; a Board with one has `Some(concrete_clock)`. Absence
does not require fake hardware, and presence does not expose helper chips.

## Several devices of a kind

Each kind's `<Kind>Peripheral` trait takes a device by `Instance`, its position
among the Board's devices of that kind in name order, and returns one
associated type. The generator picks that type by the number of devices:

- With one device, it is the device's concrete implementation type, exactly
  as if the kind allowed only one.
- With several, it is a `Board<Kind>` enum with one variant per device, named
  after it, and a `Board<Kind>Error` enum with one variant per device for each
  error type of the kind's trait. The enum implements the kind's trait by
  matching on the variant and forwarding the call, so dispatch stays static
  and no trait object or allocation is involved.

The enums come from one macro per kind in `peripherals/api`, re-exported by
`boards/hal`: `buzzer_set!`, `power_monitor_set!`, `display_set!`, and so on.
Each has the same form; `display_set!` alone names two error types, because
`Display` has a control and a render error:

~~~rust
barracuda_board_hal::buttons_set! {
    pub enum BoardButtons, BoardButtonsError {
        FrontButtons(FrontButtonsPeripheral),
        SideButtons(SideButtonsPeripheral),
    }
}
~~~

A Plugin takes devices through the slots it declares: a `"primary"` slot
receives the primary device, and a `"*"` slot every device no other slot
takes, the primary one first. The Lua packages over Board devices use one
`"*"` slot, list their devices by Board name, and use the primary device when
a script names none, so a script written for a Board with one device runs
unchanged on a Board with several.

## Initialization failures

The generated Board composition builds every shared bus and controller first,
then initializes each device. A device whose initialization fails is logged at
error level through `log`, with its Board name, its implementation, and the
error, and its slot stays empty:

~~~text
Board peripheral `<name>` (<implementation>) failed to initialize; the Board starts without it: <error>
~~~

The Board starts without that device, exactly as if it were absent: a Plugin's
optional slot receives nothing, and the other devices work. A shared bus or
controller that cannot be built, such as an I2C or SPI bus, an RMT
transceiver, or a DMA buffer, is a wiring error that no device on it can work
around: it fails Board initialization with `GeneratedBoardError`.

A Plugin whose required slot is empty because its device failed returns
`PluginError::PeripheralUnavailable` from `register`. Plugin Manager logs it,
leaves that Plugin and every Plugin depending on it out, and starts the rest of
System.

## Button events

`Buttons::read` samples whether each button is down now, and
`Buttons::poll_event` returns what happened to the buttons since, oldest
first: `Pressed`, `Released`, `Click` for a press released before the
long-press time, and `LongPress` once a press has lasted that long, while the
button is still down. Each event names the button by its snapshot index.
Reading the state never consumes events, and taking events never hides a
press from the next state read.

Implementations that sample button levels (`gpio-buttons`,
`pi4ioe5v6408-buttons`, `powerhub-buttons`, `adc-ladder-buttons`,
`capacitive-touch-buttons`, and `m5pm1-buttons`) derive events with the
`ButtonTracker` in `peripherals/api`, sampling when polled and no event waits.
It applies M5Unified's `Button_Class` rule: a new level counts once it has
held for the debounce time, or at once when the previous sample is older than
that. Each takes `debounce-ms` (10 ms) and `long-press-ms` (500 ms), M5Unified's
defaults; `m5pm1-buttons` takes only `long-press-ms`, because the M5PM1 reports
a settled level, and reports a press that came and went between two samples
as `Pressed`, `Released`, `Click`. `axp192-axp2101-buttons` reports each press
the PMIC latched, at once: `Pressed`, `Released`, `Click` for a short press and
`Pressed`, `LongPress`, `Released` for a long one, the long-press time being
the PMIC's own. Each implementation holds at most 16 events and drops the
oldest when a reader falls behind.

## Implementation manifests

Every selectable implementation owns
`peripherals/impl/<peripheral>/<implementation-id>/peripheral.yml`. The parent
directory equals `peripheral`, and the leaf directory equals `id`. Version 1
manifests declare:

- the stable implementation ID and semantic peripheral API;
- Cargo and Rust construction templates used only by code generation;
- named hardware binding roles and safe output initialization policies;
- typed parameters, defaults, enum domains, and Rust value mappings.

`peripherals/config::PERIPHERAL_APIS` is the registration boundary. An unknown
semantic kind is rejected with an instruction to add its API trait before its
first implementation. The generator understands binding categories and
ownership but contains no match on concrete implementation IDs.

`cargo board sync` validates every manifest and maintains workspace dependencies.
`cargo board select <board>` resolves the selected Board against those schemas,
checks Platform HAL support, and writes only the selected implementation
dependencies to `boards/selected/Cargo.toml`.

## Private helper chips

Helper chips are implementation details unless they independently provide a
semantic peripheral that System consumes. An I/O expander used for reset,
enable, interrupt, or power-control signals is therefore not automatically a
Board peripheral.

On M5Stack Tab5, the PI4IOE5V6408 at `0x43` is hidden this way:

- the audio-codec implementation owns the speaker-amplifier enable pin;
- the display implementation owns the panel and touch reset pins: it
  identifies the panel by the touch controller that answers, so it takes both
  out of reset, as M5GFX does;
- the camera implementation owns the sensor reset pin.

All three use `drivers/chips/pi4ioe5v6408`; none exposes the expander, its pins,
or a generic system-controller peripheral to System. Other PI4-controlled
signals must likewise be owned by the concrete semantic service they enable.

On M5Stack CoreP4X, `corep4x-dsi-display` hides the M5IOE1 expander at
`0x4F` (panel power, reset, and PWM backlight) and the M5PM1 power controller
at `0x6E` (the 5 V boost) the same way, through `drivers/chips/m5ioe1` and
`drivers/chips/m5pm1`. The Paper Mono's `paper-mono-display` uses the same two
drivers for its panel supply and reset and its front light; `paper-color-display`
and `paper-diy-display` use the M5PM1 for the e-paper supply.

A helper chip that also provides a semantic peripheral is shared by register,
never by two owners of one register. On the Core2, Tough, Station, StickC,
and CoreS3, `m5stack-pmic-display` drives the AXP192 or AXP2101 regulators,
while `axp192-axp2101-power-monitor` reads the same PMIC's battery through its
own view of the bus and touches only the status, ADC, and fuel-gauge
registers. `axp192-axp2101-vibration` writes only the Core2 motor
regulator's voltage field and enable bit beside them, and
`m5ioe1-vibration` only the StopWatch's M5IOE1 PWM channel and its pin.
`axp192-axp2101-buttons` sets only the power key's two interrupt-enable
bits and clears only its two status bits, which are write-1-to-clear, so
every other interrupt's status stays as it was. `m5pm1-power-monitor` and
`pi4ioe5v6408-buttons` likewise configure only their own M5PM1 or expander
pins next to the display implementations that use the others, and
`m5pm1-buttons` reads only the M5PM1's button-status register and sets
only the single-click-reset-disable bit of its button configuration. The
`ina3221-power-monitor` devices on the channels of one INA3221 each read
only their own channel and never write the chip.

The M5Stack PowerHub's STM32G031 power co-processor relays four semantic
peripherals, so four implementations share it the same way:
`powerhub-buttons` reads only its button register, `powerhub-led-strip`
writes only the LED supply, color, and brightness registers,
`powerhub-power-monitor` only the metering enable and the battery registers,
and `powerhub-rtc` only the clock registers. All four use
`drivers/chips/m5powerhub`.

## Stable construction and runtime behavior

`PeripheralImplementation` declares move-only `Bindings`, validated `Config`,
the returned semantic `Peripheral`, and its initialization `Error`. Its future
is unboxed and monomorphized.

Platform HAL modules convert vendor tokens into `embedded-hal`,
`embedded-hal-async`, or narrow data-plane contracts such as DSI, MIPI-CSI,
camera capture, and PCM. Peripheral implementations depend on those contracts,
not vendor HALs. Chip drivers normally depend only on upstream protocol traits.

For DSI displays, the Platform binding establishes the link and transmits raw
DBI commands, the chip driver owns the controller command sequence, and the
display implementation selects timing and applies the required delays. This
keeps controller registers out of both the semantic API and the Platform HAL.

Generated code constructs each selected implementation directly and stores its
semantic result in `GeneratedPeripherals`. System and Plugins consume those
semantic values and never reconstruct implementations from raw pins.

## Adding hardware

Adding a Board that reuses existing implementations normally requires only
`board.yml` wiring and native layout artifacts. Adding a new chip behind an
existing semantic peripheral adds a chip driver when needed, one peripheral
implementation, and its manifest. Adding a genuinely new semantic peripheral
starts with its API trait and optional ownership slot, then adds implementations.

A new kind is one additive change in four places, each next to its
neighbours:

1. `peripherals/api`: the semantic trait, its `<Kind>Peripheral` trait with a
   `take_<kind>(instance)` function, and its `<kind>_set!` macro in
   `src/sets.rs`, built from the shared helpers there. The macro forwards
   every trait method, default methods included, and awaits the async ones;
   it declares one set error type per associated error type.
2. `boards/hal`: re-export the macro, and add the kind's `Unavailable<Kind>`
   type and its `NoPeripherals` implementation; `core/system` adds the
   `<Kind>Peripheral` bound, with its device's `Send` and error `Debug`
   bounds, to the peripherals it hands Plugins.
3. `peripherals/config`: register the kind in `PERIPHERAL_APIS` and add one
   `ClaimableKind` entry to `CLAIMABLE_KINDS`, naming the trait, the take
   function, the associated type, the unavailable type, the set macro, and
   the set's error suffixes. The generator has no other per-kind code.
4. Tests: a two-device case for the macro in `peripherals/api/tests/sets.rs`
   and the kind in the `CLAIMABLE_KINDS` list of
   `peripherals/config/tests/catalog.rs`, which checks every registered kind
   renders a set.

This keeps Board count from multiplying Rust code: reusable chip behavior,
semantic adaptation, Platform resource construction, and product wiring each
live in one layer.
