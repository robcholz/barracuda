L’interface de l’appareil Barracuda repose sur trois couches : **le système**,
**les applications système** et **les applications installables**. Chaque écran,
chaque geste et chaque application appartient à exactement une d’entre elles, et
la couche détermine qui en est propriétaire, ce qu’il peut faire et ce qui se
passe en cas d’échec. Ce document fait autorité pour cette répartition ; la
conception de chaque écran se trouve dans la conception de l’interface de
l’appareil, et les contrats dans la documentation des Plugins.

| | Système | Application système | Application installable |
| --- | --- | --- | --- |
| Ce que c’est | du Rust natif dans le Plugin `app-manager` | une application intégrée : un conteneur d’application fourni par un autre Plugin | un conteneur d’application installé par la personne |
| Où elle se trouve | `/resources/view` du Plugin `app-manager` | `/resources/app` de son Plugin `builtin-app-<name>` | `/media/apps/<id>` du Plugin `app-manager` |
| S’exécute en tant que | la tâche `app-manager` | une exécution Lua avec une vue MicroTS, sous le cycle de vie des applications | idem |
| Paquets Lua | aucun | tous les paquets enregistrés, y compris le sien | les paquets ambiants et ceux que nomme son manifeste ; jamais le paquet d’une application intégrée |
| Supprimable | non | non ; seulement les infos de l’application ; une carte omet son Plugin | oui ; infos de l’application et désinstallation |
| En cas d’échec | l’appareil est hors d’usage | le système indique qu’elle s’est arrêtée | idem |
| Exemples | l’accueil et les états de l’Agent, le lanceur, le sélecteur d’applications, les centres de notifications et de contrôle, le lancement, l’arrêt, l’installation, le menu et les infos d’application | Sessions, Workflows, Files, Settings | les exemples de qualité de l’air, de bande lumineuse, de caméra et de compteur |

## Les Plugins

| Plugin | Contient |
| --- | --- |
| `app-manager` | le kit d’applications (applications, installations, cycle de vie, paquet `app`), le kit d’interface (vues, écran, tactile, gestes, polices et icônes système) et le point d’entrée qui les relie et exécute l’interface système |
| `builtin-app-<name>` | une application système : son conteneur et le backend de son propre paquet Lua |
| `system-fonts` | les polices système avec lesquelles dessine chaque vue d’un écran |
| `system-wifi` | le Wi-Fi dans l’interface système : la liaison, la carte hors ligne et le point d’accès de configuration qu’ouvre la tuile du portail, via `SystemNetwork` d’`app-manager` |

Le kit d’applications n’a pas besoin d’écran. Sur une carte sans écran, le
Plugin `app-manager` n’exécute ni kit d’interface ni interface système : c’est un
gestionnaire d’applications sans interface, et les applications avec des vues
répondent `no_display`. L’interface système n’a pas non plus besoin du réseau :
elle n’affiche un réseau que lorsqu’un Plugin en affiche un avec
`SystemNetwork`, comme le fait `system-wifi`. Une carte dotée d’un écran nomme le
profil `screen`, ou `screen-offline` pour un produit qui ne se connecte jamais au
réseau (pas de Wi-Fi, de portail, d’Agent, de Sessions ni de Settings) ; tous
deux incluent la couche `ui` : `app-manager`, `system-fonts` et les applications
intégrées qui n’ont pas besoin du réseau. Les profils sont décrits dans
[Profils de carte](/fr/boards/profiles). Une carte omet une application système
en n’activant pas son Plugin, et une carte sans écran n’active ni les
applications système ni `system-fonts`.

## Choisir la couche

Placez une fonctionnalité dans le **système** si l’une de ces conditions est
remplie :

- elle doit fonctionner quand une application se bloque ou plante, ou quand
  aucune application ne tourne ;
- elle arbitre entre les applications : ce qui est à l’écran, quelle
  application est au premier plan, quelles applications tournent ;
- elle accorde la confiance : installation, désinstallation et ce qu’une
  application peut utiliser ;
- elle répond à une saisie valable partout : balayages depuis les bords,
  retour, appuis longs sur les surfaces système, et les touches accueil et Agent
  de la carte.

Faites-en une **application système** s’il s’agit d’une expérience plein écran
livrée avec l’appareil, qui a besoin d’un état de l’appareil qu’une application
installable ne pourrait obtenir sans le demander, et qui peut échouer sans
mettre l’appareil hors d’usage : Settings, conversations, Workflows, fichiers.

Tout le reste est une **application installable** : elle est proposée dans le
Workspace par le portail, un Agent ou un autre Plugin, et la personne
l’installe.

## Le système

L’interface système du Plugin `app-manager` est le système. C’est le seul
appelant qui bascule et désinstalle des applications pour la personne, le seul
propriétaire des gestes système et, avec la page de portail du Plugin
`app-portal` sur le point d’accès de configuration de l’appareil, le seul moyen
pour la personne d’installer des applications. Sa vue se trouve sur la couche
système, au-dessus de la couche des applications : tant qu’une application est
au premier plan et qu’aucun écran système ne la recouvre, la vue de
l’application s’affiche ; tout écran système recouvre l’application et bloque
ses saisies (`AppManager::set_interactive`) jusqu’à sa fermeture.

Le kit d’interface transforme le tactile en tapotements, qui appuient sur la vue
affichée, et en appuis longs et balayages, qui ne vont qu’au système
(`UiService::next_gesture`). Les applications ne voient jamais les gestes
système : aucune application ne peut donc priver la personne de son moyen de
sortir.

Les avis atteignent la personne via le centre de notifications du système, où
tout Plugin publie avec la capacité `Notifications`, et les Workflows avec
`app.notify`. Une question qui exige une réponse de la personne
(`Notifications::ask`, `app.confirm`) est listée en premier et reste affichée sur
l’écran d’accueil jusqu’à ce qu’on y réponde. L’écran d’accueil affiche aussi
l’état de l’Agent (veille, écoute, réflexion, réponse) depuis `AgentStatus` ou
`app.agent`. Une application ne dessine jamais par-dessus une autre application
ni par-dessus le système.

Les réglages de l’appareil (luminosité, volume, sourdine, microphone, ne pas
déranger et délai de mise en veille de l’écran) relèvent de la capacité
`Preferences` : le centre de contrôle et l’application Settings modifient les
mêmes valeurs, et l’interface système applique la luminosité et le délai à
l’écran et les conserve après un redémarrage.

Un balayage vers la droite sur une application correspond au retour : une
application qui a signalé des pages avec `app.navigation(depth)` reçoit
`app:back` tant que sa profondeur est supérieure à zéro ; sinon, l’application
passe en arrière-plan et le lanceur s’affiche.

## Applications système

Une application système est une application intégrée : un Plugin
`builtin-app-<name>` dépend d’`app-manager` et ajoute son conteneur avec
`AppManager::add_builtin`. Seuls les Plugins présents dans l’image peuvent le
faire : rien de ce qui est installé ne peut créer une application système. Les
applications système suivent le même cycle de vie que toute application (active,
inactive, arrière-plan, suspendue, en cours d’arrêt) et peuvent faire `require`
sur tout paquet Lua enregistré sans le déclarer. Aucune application installée ne
peut prendre l’ID d’une application système, et les applications système ne
peuvent pas être désinstallées.

Une application intégrée accède à l’appareil par son propre paquet Lua, comme
`settings`, dont le backend se trouve dans son Plugin et ne lit que les
capacités dont ce Plugin dépend. Une application installable dont le manifeste
demande le paquet d’une application intégrée est invalide. Une application
intégrée peut indiquer pour quoi l’interface système l’ouvre, par exemple
`wifi` pour la tuile Wi-Fi du centre de contrôle : l’interface système ne nomme
ainsi jamais une application. Les applications système dessinent avec les
polices système et ne fournissent pas d’atlas propres.

## Applications installables

Une application installable commence comme un conteneur proposé dans le
Workspace sous `/workspace/media/apps/<id>` ; elle n’y est pas lançable. Elle est
écrite pour l’API d’application
([API d’application](/fr/plugins/app-manager/app-api)) : son manifeste nomme la
version du paquet `app`, les paquets stables qu’elle exige ou utilise avec la
version minimale nécessaire, les autres paquets qu’elle demande, et les cartes
auxquelles elle est destinée lorsqu’elle dialogue avec leur matériel. Le système
la vérifie par rapport à l’appareil ; une application qui ne peut pas s’exécuter
ici indique pourquoi et ne peut pas être installée. Sinon, l’écran
d’installation liste ce qu’elle demande, dans les termes que déclare le Plugin
de chaque paquet ; quand la personne l’installe, le Plugin `app-manager` copie
le conteneur dans son répertoire privé `/media/apps/<id>`, et dès lors chacune de
ses exécutions ne peut faire `require` que sur les paquets ambiants et ceux
qu’elle a nommés.
Un Workflow ou un Agent demande une installation avec `app.install` ; seule la
personne la mène à bien, sur l’écran d’installation de l’appareil ou, sur la
page Apps du portail, depuis un téléphone connecté au point d’accès de
configuration de l’appareil — c’est ainsi qu’une carte sans écran installe des
applications. Dans les deux cas, l’installation prend exactement ce qui a été
montré à la personne : l’empreinte de l’offre est figée au moment de la
demande. Une offre peut être un paquet `.bapp` signé ; une application installée
depuis un tel paquet n’accepte de mises à jour que du même signataire. La
désinstallation supprime le conteneur et les données de l’application ; l’offre
du Workspace reste jusqu’à ce que son auteur la retire.

## Polices

Le Plugin `system-fonts` intègre les polices système dans son
`/resources/fonts` et les transmet au kit d’interface via `SystemFonts`
d’`app-manager` ; une carte d’appareil l’active, et une carte sans écran omet ses
2,4 Mo. Il s’agit de Noto Sans SC aux tailles utilisées par la vue système et les
applications système, avec les caractères de son propre `charset.txt`, et des
glyphes de la police d’icônes système aux tailles où les icônes sont dessinées.
L’emplacement 16 px regular est celui de la prose : il contient aussi les
3 755 caractères courants de GB 2312, si bien que le texte dont aucune source
ne fournit les caractères — réponse d’un Agent, avis, titre de conversation —
y est dessiné. Une vue qui ne fournit pas d’atlas pour un emplacement de police
dessine avec la police système correspondante : les applications installables
peuvent donc aussi les utiliser ; une application qui affiche d’autres
caractères intègre les siens. Un texte contenant des caractères absents d’un
atlas affiche une boîte de substitution.
