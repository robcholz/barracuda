---
title: "Compiler et exécuter"
description: "Sélectionnez une carte une fois, puis compilez, flashez et exécutez-la avec les commandes Cargo habituelles."
---

Sélectionnez une carte une fois ; chaque `cargo build` et `cargo run` ultérieur
l’utilise. Sur une carte d’appareil, `cargo run` compile le firmware, le flashe
et garde les journaux dans ce terminal.

```bash
cargo board select
cargo run
```

Une carte hôte (`local-linux`, `local-macos`) a aussi besoin de l’adresse de
bouclage de son gestionnaire de périphériques virtuels :
`BARRACUDA_VIRTUAL_IO_ADDR=127.0.0.1:7878 cargo run` (voir
[Virtual IO](/platforms/virtual-io)).

La première commande ouvre une liste de cartes en couleur. Déplacez-vous avec
les flèches, tapez pour une recherche approximative et appuyez sur Entrée pour
sélectionner. Elle valide le paquet de la carte et enregistre la sélection dans
un état local ignoré par git. Elle résout la plateforme auto-décrite
correspondante, met à jour les blocs de dépendances statiques de la plateforme
et du HAL de carte sélectionnés, et écrit localement la configuration de la
cible et du runner. La plateforme résolue fournit sa chaîne d’outils rustup, sa
politique `build-std` optionnelle, l’environnement généré par l’installateur et
l’invite d’installation affichée quand cette chaîne d’outils est absente. La
sélection active la chaîne d’outils comme surcharge de l’espace de travail et
importe son environnement : les commandes ordinaires `cargo build` et
`cargo run` agissent donc directement sur l’application System autonome via
Cargo natif ; il n’y a ni enveloppe de compilation dépendante de la carte, ni
étape de configuration du shell. Les cartes d’appareil compilent le firmware
avec `--release`. Les journaux du System, de la plateforme, du Core et des
Plugins restent dans ce terminal.

Lancez séparément le canal terminal externe. Cette commande est toujours
compilée pour l’hôte de développement, même quand la carte sélectionnée utilise
une cible embarquée :

```bash
cargo cli
cargo cli configure
```

`cargo cli` ouvre un sélecteur Local/Remote. Local affiche et utilise l’adresse
de l’espace de travail actif publiée par le lanceur macOS, ou le point d’accès
Linux `http://10.42.0.2:8787`. Remote demande l’adresse IPv4 ou IPv6 d’un
appareil et se connecte à son WebServer sur le port 8787.

`cargo cli configure` utilise le même sélecteur Local/Remote, puis vous guide
dans un formulaire de configuration dans le terminal : modèles, recherche web,
et canaux WeChat, QQ, BlueBubbles, Telegram et Inkbox. La page de réglages
complète de chaque Plugin se trouve dans le
[portail de l’appareil](/fr/use/device-portal). Passez une adresse explicite pour
sauter la sélection :

```bash
cargo cli configure http://DEVICE_ADDRESS:8787
```

Par défaut, la compilation règle la journalisation de la plateforme sur `info`.
Définissez `BARRACUDA_LOG_LEVEL` pour une compilation afin de choisir `off`,
`error`, `warn`, `info`, `debug` ou `trace` :

```bash
BARRACUDA_LOG_LEVEL=debug cargo run
```

Le niveau choisi est validé et intégré au binaire de la plateforme ; il n’est
pas lu depuis l’environnement à l’exécution.

L’automatisation peut contourner l’invite avec `cargo board select <board-name>`.

Quand ils ajoutent une plateforme ou un HAL de carte, les mainteneurs mettent à
jour une fois les registres suivis et committent les blocs générés :

```bash
cargo platform sync
cargo board sync
```

La CI peut les valider sans rien écrire grâce aux variantes `--check`
correspondantes. Récupérer un commit à jour ne demande jamais d’étape de
synchronisation supplémentaire.

Les noms de carte disponibles sont les noms des répertoires sous
`boards/configs/`. Le `toolchain.target` d’une carte d’appareil devient la cible
de compilation Cargo locale ; les cartes hôtes l’omettent.

Le profileur de mémoire est une charge de travail exécutable plutôt qu’un banc
d’essai de débit :

```bash
cargo run --profile profiling -p barracuda-agent-profile -- agent-init
```
