L’API d’application est ce sur quoi une application installable peut compter
d’un appareil à l’autre : les paquets Lua qu’elle peut utiliser, ce qu’elle peut
demander à l’appareil, et les règles qui maintiennent ces deux éléments stables.
Elle comporte deux parties. Le paquet `app`, celui de ce Plugin, a une version,
le **niveau d’API** ; ce système implémente le niveau 1, et une application
indique le niveau pour lequel elle est écrite dans le champ `api` de son
manifeste (voir [Format d’application](/fr/plugins/app-manager/app-format)). Tous
les autres paquets sont ceux que l’appareil enregistre, chacun indiquant ce
qu’il garantit.

Les applications système ne sont pas soumises à l’API d’application : elles sont
livrées dans l’image et peuvent faire `require` sur n’importe quel paquet.

## Paquets

Un Plugin qui enregistre un paquet Lua déclare ce qu’il garantit avec
`LuaPackage::interface`, ainsi que la ligne qui le décrit sur l’écran
d’installation. Ce Plugin lit ces déclarations dans le `LuaPackageRegistry` ; il
ne nomme le paquet d’aucun autre Plugin : ce qu’un appareil offre aux
applications est donc exactement ce qu’enregistrent ses Plugins activés. Le
Plugin propre à chaque paquet documente ses fonctions et la version dans
laquelle chacune est apparue.

| Interface | Comment une application l’obtient | Identique sur tous les appareils |
| --- | --- | --- |
| Ambiante | toujours, sans le demander | oui |
| Stable, avec une version | `requires` ou `uses` dans le manifeste, sous la forme `name` ou `name@version` | oui, là où l’appareil la possède |
| Propre à une carte | `permissions`, avec `boards` | non : elle dialogue avec le matériel d’une carte précise |
| Aucune | `permissions` | aucune garantie |

Un paquet qui a besoin d’un composant de la carte ne déclare rien tant que la
carte ne possède pas ce composant : sur une telle carte, une application qui
l’exige n’est donc pas installée.

Les paquets propres à ce Plugin :

| Paquet | Interface | API Lua |
| --- | --- | --- |
| `app` | ambiante, version 1 | l’application elle-même : événements, vue, stockage, `app.device()` ([Format d’application](/fr/plugins/app-manager/app-format)) |
| `notify` | stable, version 2 | `notify.post`, `notify.ask` (ci-dessous) |

### `notify`

- `notify.post(title [, body]) -> id` ajoute un avis au centre de
  notifications.
- `notify.ask(title [, body [, allow, deny]]) -> allowed` interroge la personne
  sur une carte listée avant tous les avis et attend sa réponse : `true` si elle
  accepte, `false` si elle refuse ou ferme la carte. À partir de la version 2,
  `allow` et `deny` nomment les deux boutons de la carte (par défaut, des
  libellés signifiant Autoriser et Refuser ; 6 caractères au plus chacun), comme
  dans `notify.ask("Lights on?", nil, "Now", "Later")`.

Les échecs renvoient `nil` et un message.

## Vérification d’installation

Le système vérifie une application proposée par rapport à l’appareil avant de
l’installer, dans cet ordre, et s’arrête à la première raison trouvée.
`app.list` signale la raison comme `incompatible` pour l’application ; l’écran
d’installation l’affiche et désactive le bouton d’installation ; `app.install`
répond `{"error": "incompatible", "reason": …}`.

| Vérification | Ce que dit la raison |
| --- | --- |
| `api` dépasse le niveau de l’appareil | mettez à jour le système : l’application exige l’API 2, cet appareil a la 1 |
| `boards` ne liste pas cette carte | uniquement pour espressif-esp-vocat-v1-2 (les cartes listées) |
| l’application a une vue et l’appareil n’a pas d’écran | cet appareil n’a pas d’écran |
| l’écran est plus petit que `view.size` | l’écran est trop petit : l’application exige 480×480 |
| `view.shape` vaut `rect` et l’écran est rond | l’application exige un écran carré |
| un paquet de `requires` n’est pas un paquet stable ici | cet appareil n’a pas notify |
| sa version ici est inférieure à celle que nomme `requires` | mettez à jour le système : l’application exige notify version 2, cet appareil a la version 1 |
| un paquet de `permissions` est absent | cet appareil ne prend pas en charge serial |

Une application installée qui ne convient plus, après un changement de carte ou
de système, ne s’ouvre pas ; `app.open` répond `incompatible`.

### Vues et écran

Une vue est mise en page à la taille de l’écran, sans mise à l’échelle : sa
racine remplit l’écran, et la mise en page est en flexbox ; une vue qui remplit
son parent (`w-full`, `h-full`), espace ses colonnes avec des marges des deux
côtés (`left-[40px] right-[40px]`) et centre avec `justify-center` convient donc
aux écrans d’autres tailles. Les tailles fixes restent telles qu’écrites.
`view.size` est le plus petit écran où la vue tient encore, et une vue ronde,
qui reste dans le cercle inscrit, convient aussi à un écran rectangulaire ; une
vue `rect` ne convient pas à un écran rond, dont elle perdrait les coins. Le
texte garde sa taille : les emplacements de police sont pré-calculés à des
tailles fixes en pixels. Une vue qui a besoin de la taille de l’écran la lit
dans `app.device().display`.

## Exécutions

Une exécution d’une application installable peut faire `require` sur les
paquets ambiants et sur chaque paquet que son manifeste nomme dans `requires`,
`uses` et `permissions`. Un paquet que l’application n’a pas nommé n’est pas
disponible, et `require` échoue. Un paquet de `uses` peut être absent ou plus
ancien que souhaité : vérifiez `app.device().capabilities` avant de l’exiger, ou
appelez `pcall(require, name)`.

`app.device()` décrit l’appareil ; `capabilities` associe chaque paquet stable à
sa version :

```lua
{
  api = 1,
  board = "espressif-esp-vocat-v1-2",
  display = { width = 360, height = 360, round = true },  -- nil without one
  touch = true,
  capabilities = { notify = 2, ... },
}
```

## Versions

- L’interface d’un paquet stable ne change jamais une fois déclarée : aucune
  fonction n’est supprimée, renommée, ni dotée d’autres arguments ou résultats.
- Ajouter des fonctions augmente la version du paquet ; son Plugin documente ce
  que chaque version a ajouté.
- Un changement incompatible donne un nouveau paquet avec un nouveau nom ;
  l’ancien reste.
- Le paquet `app` suit les mêmes règles, avec le niveau d’API comme version.
- Un paquet propre à une carte, ou qui ne garantit rien, peut changer à chaque
  mise à jour du système ; c’est pourquoi les applications qui l’utilisent
  nomment leurs cartes.
