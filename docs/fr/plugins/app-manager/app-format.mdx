Voici le format d’un conteneur d’application, version 1. Le Plugin
`app-manager` charge tout conteneur à ce format depuis chacun de ses
emplacements : un conteneur écrit par la compilation de l’image, par le portail
ou par un Agent est donc la même chose ; c’est son emplacement qui détermine le
type d’application (voir [Interface de l’appareil](/fr/architecture/device-ui)).
`crates/appkit/resources/app-manifest.json` est la forme lisible par machine des
règles de manifeste ci-dessous. Ce qu’une application peut utiliser, et la façon
dont un appareil décide qu’elle lui convient, relèvent de l’API d’application,
décrite dans [API d’application](/fr/plugins/app-manager/app-api).

## Emplacements

| Emplacement | Répertoire                    | Écrit par                             | Contient |
| ----------- | ----------------------------- | ------------------------------------- | ----- |
| `builtin`   | `/resources/app/` du Plugin qui la fournit | la compilation de l’image (lecture seule) | les applications système |
| `installed` | `/media/apps/<id>/`           | le Plugin `app-manager` à l’installation (privé) | les applications installables |
| `workspace` | `/workspace/media/apps/<id>/` ou `<id>.bapp` | le portail, les Agents, d’autres Plugins (Workspace partagé) | les applications proposées à l’installation |

Un Plugin d’application intégrée transmet son système de fichiers au Plugin
`app-manager`, dont la portée propre contient les deux autres ; il ne fait que
lire le Workspace. Les applications intégrées et installées sont lançables ; un
conteneur du Workspace est une offre. L’installer copie le manifeste et les
fichiers qu’il nomme dans `/media/apps/<id>/`, en remplaçant une application
installée d’une autre version. L’ID d’une application système lui appartient :
aucun conteneur ailleurs ne peut l’utiliser, et `app.list` signale comme invalide
un conteneur qui le fait.

## Conteneur

Un conteneur est un répertoire portant l’ID de l’application, qui contient côte
à côte un manifeste et les fichiers qu’il nomme :

```text
<id>/
  app.json          the manifest
  main.lua          the entry program (or the file `entry` names)
  view.bvir         optional view program        ┐
  styles.bin        its compiled stylesheet      ├ named by `view`
  font-1.bin …      its baked font atlases       ┘
```

Les autres fichiers sont ignorés. Les répertoires dont le nom commence par `.`
sont sautés.

## Paquets

Dans le Workspace, une application peut aussi être proposée sous la forme d’un
seul fichier, `/workspace/media/apps/<id>.bapp`, qui contient les mêmes fichiers
et peut être signé. Un ID proposé à la fois comme répertoire et comme paquet est
invalide. `resources/pack-app.ts` écrit les paquets :

```sh
bun resources/pack-app.ts --new-key key.jwk                 # once, and keep it
bun resources/pack-app.ts <bundle> <id>.bapp --key key.jwk  # sign a built container
bun resources/pack-app.ts <bundle> <id>.bapp                # or leave it unsigned
```

Tous les nombres sont en little-endian :

| Décalage | Taille | Contenu |
| --- | --- | --- |
| 0 | 4 | `BAPP` |
| 4 | 1 | version du format, 1 |
| 5 | 1 | nombre de fichiers, de 1 à 64 |
| 6 | 1 | drapeaux : bit 0, un bloc de signature suit |
| 7 | 1 | 0 |
| 8 | 4 | la longueur du contenu : cet en-tête, le répertoire et les fichiers |
| 12 | 40 par fichier | le répertoire : le nom du fichier, complété par des NUL jusqu’à 32 octets, puis son décalage et sa longueur (4 octets chacun) |
| … | | les fichiers, chacun à l’endroit qu’indique son entrée |
| longueur du contenu | 133 | si signé : `BSIG`, la clé publique P-256 SEC1 non compressée (65 octets) et la signature ECDSA du contenu avec SHA-256 sous la forme `r ‖ s` (64 octets) |

Le listage ne lit que l’en-tête et le répertoire. Quand une installation est
demandée, l’appareil hache le contenu avec SHA-256 et vérifie la signature : un
paquet dont la signature échoue est invalide, et l’écran d’installation affiche
le signataire d’un paquet signé par les premiers octets du SHA-256 de sa clé, ou
indique qu’il n’est pas signé. L’installation prend exactement ce qui a été
montré à la personne : l’empreinte est figée, et une offre modifiée entre-temps
répond `Changed`. Une offre sous forme de répertoire est figée de la même façon,
par le SHA-256 de ses fichiers.

Une application installée depuis un paquet signé conserve la clé de son
signataire à côté de son conteneur et n’accepte ensuite que les paquets signés
par cette clé : un paquet d’une autre clé, un paquet non signé ou un répertoire
ne proposent aucune mise à jour et indiquent pourquoi. Une application installée
sans signature accepte n’importe quelle mise à jour.

## Manifeste

```json
{
  "format": 1,
  "id": "counter",
  "name": "Counter",
  "version": "0.1.0",
  "api": 1,
  "requires": ["notify@2"],
  "entry": "main.lua",
  "view": {
    "program": "view.bvir",
    "styles": "styles.bin",
    "fonts": ["font-1.bin", "font-2.bin", "font-12.bin"],
    "size": [360, 360],
    "shape": "round"
  }
}
```

| Champ          | Obligatoire | Règle                                                    |
| -------------- | -------- | ----------------------------------------------------------- |
| `format`       | oui      | `1`                                                         |
| `id`           | oui      | 1 à 32 caractères parmi `a-z`, `0-9`, `-` ; égal au nom du répertoire |
| `name`         | oui      | nom affiché, 1 à 64 caractères                              |
| `version`      | oui      | la chaîne de version de l’auteur, 1 à 32 caractères         |
| `icon`         | non      | le nom d’une icône système, comme `lamp`, affichée dans le lanceur ; sans icône, le lanceur affiche le premier caractère du nom |
| `entry`        | non      | le programme Lua à exécuter ; par défaut `main.lua`         |
| `view`         | non      | à omettre pour une application sans interface               |
| `view.program` | avec une vue | le programme de vue BVIR                                |
| `view.styles`  | avec une vue | la feuille de style compilée                            |
| `view.fonts`   | non      | jusqu’à 16 atlas de polices pré-calculés ; aucun par défaut |
| `view.size`    | non      | `[width, height]`, le plus petit écran où tient la vue ; la compilation l’écrit depuis `pocket.json`. La vue est mise en page à la taille de l’écran |
| `view.shape`   | non      | `round`, une vue qui reste dans le cercle inscrit et convient à tout écran, ou `rect`, une vue qui exige un écran rectangulaire |
| `api`          | non      | la version du paquet `app` pour laquelle l’application est écrite ; par défaut `1` |
| `requires`     | non      | jusqu’à 16 paquets stables sans lesquels l’application ne peut pas s’exécuter, chacun sous la forme `name` ou `name@version` avec la version minimale nécessaire |
| `uses`         | non      | jusqu’à 16 paquets stables qu’elle utilise quand l’appareil les possède, écrits comme dans `requires` |
| `permissions`  | non      | jusqu’à 16 autres paquets Lua : ceux propres à une carte et ceux qui ne garantissent rien |
| `boards`       | avec un paquet propre à une carte | les cartes auxquelles l’application est destinée, par leur nom stable |

Chaque fichier nommé est un simple nom de fichier dans le conteneur : 1 à 64
caractères parmi `A-Z`, `a-z`, `0-9`, `_`, `.`, `-`, jamais `.` ni `..`, et il
doit exister. Les champs inconnus sont rejetés : une faute de frappe est ainsi
signalée et non ignorée. Le manifeste fait au plus 4 Kio, le programme d’entrée
64 Kio, et les fichiers de vue ensemble 512 Kio.

Chaque paquet est nommé une seule fois dans l’ensemble de `requires`, `uses` et
`permissions` : les paquets stables dans les deux premiers, tout le reste dans le
troisième ; les paquets ambiants, dont dispose toute application, dans aucun. Un
paquet propre à une carte sans `boards` n’est pas valide. Qu’un paquet soit
stable, ambiant ou propre à une carte dépend de ce qu’il déclare sur l’appareil
qui lit le manifeste (`LuaPackage::interface`) : un paquet absent de cet appareil
est donc vérifié par l’appareil où l’application est installée.

Les exécutions d’une application installable peuvent faire `require` sur les
paquets ambiants et les paquets que nomme son manifeste ; un paquet qu’elle n’a
pas nommé n’est pas disponible, et `require` échoue. Avant que la personne
installe l’application, l’écran d’installation liste ce qu’elle demande dans les
termes que déclare le Plugin de chaque paquet, ou explique pourquoi cet appareil
ne peut pas l’exécuter ([API d’application](/fr/plugins/app-manager/app-api)).
Une application système peut faire `require` sur tout paquet enregistré : son
manifeste n’en nomme donc aucun. Le paquet propre à une application intégrée,
comme `settings`, est réservé aux applications intégrées : une application
installable qui en demande un n’est pas valide.

Un conteneur qui enfreint une règle n’est pas lançable. `app.list` le signale
sous `invalid` avec l’emplacement, le nom du répertoire et le problème, par
exemple `app.json: JSON schema validation failed at $.view.program: Pattern`.

## Programme

Le programme d’entrée s’exécute sur la VM comme toute exécution Lua, avec le
paquet `app` lié à cette application. La liaison partage la première ligne du
programme : les numéros de ligne des erreurs correspondent donc au fichier. Les
applications n’ont pas d’entrée standard ; une lecture obtient une fin de
fichier.

### La boucle d’événements

Chaque application est une boucle unique sur `app.events()`. Les appels de vue,
les événements de cycle de vie et les tics de minuterie arrivent dans ce flux
unique, dans l’ordre :

```lua
local app = require("app")
local view = app.view()                -- nil for a headless app

for event, a, b in app.events() do
  if event == "app:background" then save()
  elseif event == "app:terminate" then save() break
  elseif event == "increment" then ...  -- a view call: handler name, then arguments
  end
end
```

| Événement        | Quand                                                                |
| ---------------- | -------------------------------------------------------------------- |
| `app:active`     | L’application est au premier plan et reçoit les saisies. Premier événement d’une application avec vue. |
| `app:inactive`   | Toujours visible mais ne reçoit pas les saisies : une surcouche la recouvre ou une transition est en cours. Aucun appel de vue ne suit avant `app:active`. |
| `app:background` | Elle a quitté le premier plan. Sauvegardez maintenant : une application suspendue peut être arrêtée sans autre événement. |
| `app:foreground` | Elle revient de l’arrière-plan ; `app:active` suit.                  |
| `app:terminate`  | On lui demande de s’arrêter. Rendez la main dans le délai de grâce, sinon elle est annulée. |
| `app:tick`       | L’intervalle défini avec `app.events{ every = ms }` est écoulé (au moins 100 ms). Non délivré en arrière-plan ni pendant la suspension. |
| `app:back`       | La personne a balayé pour revenir alors que l’application avait signalé, avec `app.navigation`, une page plus profonde que la première. Affichez la page précédente et signalez sa profondeur. |

Après `app:background`, le programme doit être revenu dans `app.events()` dans
le délai de grâce (1 s) ; il est alors suspendu : il n’utilise pas de CPU, et
son arbre de vue est libéré puis reconstruit à partir de ses valeurs à son
retour. Un programme encore occupé à la fin du délai de grâce est annulé, tout
comme un programme qui ignore `app:terminate`. La boucle se termine après
`app.exit()` ; le programme rend alors la main.

Les applications sans interface ne passent jamais au premier plan. Elles
s’exécutent comme des services et ne voient que `app:tick` et `app:terminate`.

### API

| Appel | Résultat |
| ---- | ------ |
| `app.id`, `app.name`, `app.version` | Issus du manifeste. |
| `app.device()` | La version du paquet `app`, la carte, l’écran, le tactile et les paquets stables avec leurs versions ([API d’application](/fr/plugins/app-manager/app-api)). |
| `app.view()` | La vue, ou `nil` pour une application sans interface. |
| `app.events([{ every = ms }])` | L’itérateur d’événements ; `every` démarre une minuterie. |
| `app.exit()` | Termine la boucle d’événements. |
| `app.navigation(depth)` | Indique à quelle profondeur de pages se trouve l’application ; 0, la valeur par défaut, est sa première page. Un balayage retour délivre `app:back` tant que la profondeur est supérieure à 0, et laisse l’application à 0. |
| `view:set(name, value)` | Écrit une valeur déclarée par le `app.d.ts` de la vue ; vérifiée par rapport à son type. |
| `view:is_open()`, `view:close()` | L’état de la vue ; la fermer met fin aux appels de vue. |
| `app.kv.get(key)` | La valeur stockée, ou `nil`. |
| `app.kv.set(key, value)` | Stocke des booléens, des nombres, des chaînes et des tables qui sont des tableaux ou ont des clés de type chaîne ; `nil` supprime. |
| `app.kv.delete(key)`, `app.kv.keys()` | Supprime une clé ; liste les clés, triées. |
| `app.fs.read(path)`, `app.fs.write(path, data)`, `app.fs.append(path, data)` | Accès au fichier entier ; les écritures remplacent de façon atomique. |
| `app.fs.list([dir])` | Noms triés ; les répertoires se terminent par `/`. |
| `app.fs.exists(path)`, `app.fs.remove(path)`, `app.fs.mkdir(path)` | Gestion simple des fichiers. |

Les échecs renvoient `nil` et un message au lieu de lever une erreur :
`assert(...)` les transforme donc en erreurs. Les clés font 1 à 64 octets et le
stockage contient au plus 16 Kio de JSON. Les fichiers font au plus 64 Kio ; les
chemins sont relatifs à l’arborescence de fichiers propre à l’application, avec
au plus 8 niveaux, sans `.` ni `..`.

Le stockage appartient à l’ID de l’application, pas au conteneur : il se trouve
dans le répertoire privé `/media/data/<id>/` de l’App Manager (`kv.json` et
`files/`), survit aux mises à jour et aux redémarrages, et n’est jamais visible
des autres applications.

## Vues

`view.program`, `view.styles`, `view.fonts` et `view.size` sont des produits de
compilation : le compilateur MicroTS transforme `app.tsx` et son contrat
`app.d.ts` en View IR, `ui-link` le lie en BVIR, et le générateur de polices
produit les atlas. Le `view` d’un manifeste source ne contient que `shape`. Un
Agent qui ne peut pas exécuter cette chaîne d’outils écrit une application sans
interface, ou copie les fichiers de vue d’une compilation existante à côté de
son propre programme d’entrée.

## Exemple : une application sans interface qu’un Agent peut proposer

`/workspace/media/apps/hello/app.json` :

```json
{ "format": 1, "id": "hello", "name": "Hello", "version": "1" }
```

`/workspace/media/apps/hello/main.lua` :

```lua
local app = require("app")
local runs = (app.kv.get("runs") or 0) + 1
assert(app.kv.set("runs", runs))
print("hello from " .. app.id .. ", run " .. runs)
```

Proposez-la avec `app.install` et `{"id":"hello"}` : l’appareil affiche l’écran
d’installation et, une fois que la personne l’a installée, ouvrez-la avec
`app.open` et `{"id":"hello"}` ; `app.status` affiche alors `last_exit.output`
sous la forme `["hello from hello, run 1"]`. `crates/appkit/tests/fixtures/`
contient des exemples d’applications compilées avec vues, chacune prête à être
copiée dans `/workspace/media/apps/<id>/` : `air` (une application de qualité de
l’air, sans paquet), `lamp` (une application de bande lumineuse, exige `light`),
`camera` (une application de caméra, exige `camera`) et `counter` (un compteur,
sans paquet).
