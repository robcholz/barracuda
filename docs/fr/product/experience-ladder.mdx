Barracuda se vit comme une échelle. Chaque niveau demande un peu plus à la
personne et lui donne beaucoup plus de liberté. Chaque niveau est utile en soi ;
personne n’a besoin de monter plus haut que son projet ne l’exige. À chaque
niveau, un agent fait le gros du travail.

| Niveau | Nom | Qui | Ce qu’ils font | Où | Agent | Par où commencer |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | Prêt à l’emploi | Tout le monde | Installer depuis le navigateur, puis demander des choses à la carte | Navigateur, téléphone, appareil | L’Agent embarqué écrit et exécute des scripts VM | [Portail de l’appareil](/fr/use/device-portal) |
| 2 | Configurer | Makers, enseignants | Choisir les Plugins du firmware, compiler et flasher | Machine du développeur | — (configuration, pas génération) | [Profils de carte](/fr/boards/profiles) |
| 3 | Créer des applications | Développeurs d’applications | Décrire une application, générer sa logique et son interface, la flasher | Live Editor (navigateur) | Agent du navigateur | [Interface de l’appareil](/fr/architecture/device-ui) |
| 4 | Créer des Plugins | Développeurs de Plugins | Ajouter de nouvelles capacités au runtime | Machine du développeur | Agent de code + skill `create-plugin` | [Écrire un Plugin](/fr/develop/write-a-plugin) |
| 5 | Ajouter des cartes et des plateformes | Contributeurs, fabricants de cartes | Porter Barracuda sur une nouvelle carte ou une nouvelle famille de puces | Machine du développeur | Agent de code + skills `create-board`, `create-platform` | [Cartes](/boards/overview) |
| 6 | Tout personnaliser | Concepteurs de produits | Choisir ou créer la plateforme et la carte, alléger ou créer des Plugins, adapter le firmware à un budget de ressources | Machine du développeur | Agent de code + skill `fully-customize` | [Firmware sur mesure](/fr/develop/custom-firmware) |

## Niveau 1 — Prêt à l’emploi

**Dans la documentation :** [Portail de l’appareil](/fr/use/device-portal) · [Canaux](/fr/use/channels) · [Scripts](/fr/use/scripts) · [Automatisations](/fr/use/automations)

**Objectif :** un appareil qui fonctionne, parle et agit en quelques minutes,
sans chaîne d’outils.

1. Ouvrez le Web Installer, choisissez une carte et une version, branchez l’USB,
   installez. Chaque carte reçoit un firmware par défaut avec un ensemble de
   Plugins par défaut.
2. Connectez-vous au Wi-Fi depuis la même page ; l’installateur passe la main
   au portail de l’appareil.
3. Enregistrez un modèle et liez un canal (WeChat, Telegram, QQ, iMessage, chat
   web ou terminal).
4. Demandez quelque chose de physique à la carte : « fais clignoter la LED deux
   fois par seconde », « affiche la température à l’écran », « préviens-moi
   quand la luminosité baisse ».

L’Agent embarqué répond en écrivant un court script VM et en l’exécutant
immédiatement sur le matériel réel. Le script, sa sortie et son résultat
apparaissent dans la conversation. Les comportements de longue durée sont
maintenus par les automatisations et les planifications Workflow : l’appareil
continue de travailler après la fin de la conversation.

**Ce qui le rend possible :** le Web Installer, le portail de l’appareil,
l’Agent embarqué, la VM et ses paquets de périphériques, les canaux, Workflow.

## Niveau 2 — Configurer

**Dans la documentation :** [Profils de carte](/fr/boards/profiles) · [Compiler et exécuter](/fr/get-started/build-and-run) · [CLI](/fr/reference/cli)

**Objectif :** adapter l’appareil au projet en choisissant ses Plugins, sans
écrire de code.

Les Plugins sont compilés dans le firmware : l’ensemble de Plugins se choisit
donc sur la machine du développeur. Sélectionnez la carte, choisissez les
Plugins dont le projet a besoin — caméra, écran, bande de LED, capteurs,
recherche web, un canal de messagerie —, laissez le reste de côté, puis
compilez et flashez. Il existe trois façons de choisir :

- une commande interactive qui liste les Plugins disponibles ;
- un fichier de configuration qui liste les Plugins activés, pour les projets
  suivis en gestion de versions ;
- l’agent de code du développeur, qui choisit les Plugins pour un besoin donné
  et compile le firmware.

Un Plugin laissé de côté ne coûte ni mémoire, ni flash, ni tâches. Sur
l’appareil, chaque Plugin apporte sa propre page dans le portail de l’appareil :
chaque capacité arrive avec ses propres réglages.

**Ce qui le rend possible :** les déclarations de Plugins, la compilation sur
l’hôte, les pages de portail par Plugin.

## Niveau 3 — Créer des applications

**Dans la documentation :** [Interface de l’appareil](/fr/architecture/device-ui) · [Format d’application](/fr/plugins/app-manager/app-format) · [API d’application](/fr/plugins/app-manager/app-api) · [PocketJS](/fr/plugins/app-manager/pocketjs)

**Objectif :** une véritable application d’appareil avec sa propre interface,
sans monter de projet firmware.

Dans le Live Editor, le développeur décrit l’application. L’Agent du navigateur
génère la logique de l’application et son interface ; le développeur la
prévisualise et l’améliore visuellement, puis la flashe sur la carte par USB
depuis la même page. Les applications s’exécutent sur l’appareil sous le Plugin
App Manager, qui les installe, les démarre, les arrête et les met à jour aux
côtés du reste du runtime.

**Ce qui le rend possible :** le Live Editor, l’Agent du navigateur, le Plugin
App Manager, le runtime d’applications, le flashage depuis le navigateur.

## Niveau 4 — Créer des Plugins

**Dans la documentation :** [Écrire un Plugin](/fr/develop/write-a-plugin) · [API des Plugins](/architecture/plugin-api) · [Tous les Plugins](/plugins/overview)

**Objectif :** ajouter à Barracuda une nouvelle capacité utilisable par
n’importe quel appareil.

Le développeur clone le dépôt et demande à son agent de code — Claude Code,
Cursor ou Codex — de créer un Plugin. La skill `create-plugin` transmet à
l’agent l’architecture de Barracuda : quand exposer une capacité typée, une
action ou un événement Workflow, ou un outil de l’Agent ; comment fonctionnent
le cycle de vie et la propriété des tâches ; comment le Plugin se documente ; et
quels tests ciblés écrire. Le résultat est un Plugin qui ressemble à tous les
Plugins officiels.

**Ce qui le rend possible :** le contrat des Plugins, `plugin.toml`, des
conventions d’API adaptées aux agents, la skill `create-plugin`, la
documentation par Plugin.

## Niveau 5 — Ajouter des cartes et des plateformes

**Dans la documentation :** [Cartes](/boards/overview) · [Périphériques](/boards/peripherals) · [Architecture des plateformes](/architecture/platform-architecture)

**Objectif :** porter Barracuda sur un nouveau matériel.

- **Une nouvelle carte** sur une puce prise en charge est une description :
  puce, cible de la chaîne d’outils, plan de la flash et périphériques. La skill
  `create-board` la produit avec son plan, et la carte apparaît dans le Web
  Installer.
- **Une nouvelle plateforme** apporte une nouvelle famille de puces : point
  d’entrée de l’exécuteur, pile réseau, système de fichiers, flash et
  adaptateurs HAL derrière le contrat de plateforme. La skill `create-platform`
  guide l’agent à travers ce contrat sans modifier le System ni aucun Plugin.

**Ce qui le rend possible :** le YAML de carte et le contrat de plateforme, la
sélection indépendante de la carte et de la plateforme, les skills
`create-board` et `create-platform`.

## Niveau 6 — Tout personnaliser

**Dans la documentation :** [Firmware sur mesure](/fr/develop/custom-firmware)

**Objectif :** un firmware de produit taillé exactement pour une puce, un budget
de ressources et une tâche.

Le concepteur indique la cible et les exigences. Avec la skill
`fully-customize`, l’agent de code sélectionne ou crée la plateforme et la
carte, choisit l’ensemble de Plugins, allège les Plugins trop lourds pour le
budget, crée ceux qui manquent et vérifie que le résultat tient dans la mémoire
et la flash de l’appareil. Le résultat est un firmware qui ne contient que ce
dont le produit a besoin.

**Ce qui le rend possible :** tous les niveaux inférieurs — Plugins, cartes,
plateformes et les skills qui les créent —, assemblés par un seul agent avec un
seul objectif.

## Passer d’un niveau à l’autre

- Chaque niveau transmet quelque chose de concret au suivant : le script écrit
  par l’Agent embarqué peut devenir une application ; une application qui a
  besoin d’une nouvelle capacité devient un Plugin ; un Plugin qui a besoin d’un
  nouveau matériel devient une carte.
- Rien à un niveau supérieur ne casse un niveau inférieur. Un firmware
  entièrement personnalisé s’installe toujours depuis le navigateur, dispose
  toujours d’un portail de l’appareil, et son Agent embarqué écrit toujours des
  scripts.
- La documentation est organisée par niveau : chaque lecteur commence là où il
  en est.
