title: "Write a Plugin"

---

Every capability in Barracuda is a Plugin, so adding one is how you extend the
runtime. Do it on your computer, in the repository, with the coding agent you
already use: Claude Code, Cursor, or Codex.

## Ask your coding agent

The repository ships a `create-plugin` skill at
`.agents/skills/create-plugin/SKILL.md`. It applies the
[Plugin API](/architecture/plugin-api) contract step by step, so the result
looks like every built-in Plugin.

```txt
> Read .agents/skills/create-plugin/SKILL.md, then create a Plugin that
  reads an SHT40 temperature and humidity sensor and exposes it to Lua.
```

## What the skill does

<Steps>
  <Step title="Decide the scope">
    Name the feature the Plugin owns and the Plugins whose capabilities it
    uses. Those, and only those, become its `depends-on`.
  </Step>
  <Step title="Lay out the directory">
    Create `plugins/<id>/plugin.toml` and `crates/plugin`, enable the Plugin in a
    profile or on a Board, and run `cargo plugin sync`.
  </Step>
  <Step title="Construct, register, and start">
    One constructor, `new(&mut PluginContext)`. Register contracts in
    `register`; spawn owned tasks in `start`.
  </Step>
  <Step title="Add the contracts callers need">
    A typed capability for other Plugins, Workflow Actions and Events, a Lua
    package through a `vm-<name>` Plugin, or an Agent Tool through an
    `agent-<name>` Plugin.
  </Step>
  <Step title="Test and document">
    Focused tests for the Plugin, and its page at `docs/plugins/<id>.mdx` in the
    required form.
  </Step>
</Steps>

## Check the result

```bash terminal
cargo plugin info <id>     # manifest and dependencies
cargo plugin sync --check  # conventions, and the generated registry is current
```

`cargo plugin sync` first checks every Plugin against the conventions: its
layout, schemas, page form, and crate dependencies. Run the Plugin's own
focused tests locally; leave the full test matrix to CI.
