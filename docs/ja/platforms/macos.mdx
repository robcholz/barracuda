---
title: "macOS プラットフォーム"
sidebarTitle: "macOS"
description: "特権不要のユーザー空間ネットワークゲートウェイを通じて、`sudo` なしで macOS 上で Barracuda を動かします。"
---

macOS プラットフォームはデバイス向けプラットフォームと同じ `embassy_net::Stack` を動かし、そのレイヤー 3 ドライバーを Barracuda の特権不要なユーザー空間ゲートウェイに接続します。UTUN インターフェースの作成、PF ルールの変更、ホストのフォワーディングの有効化は行わず、`sudo` も必要ありません。

- ゲストスタック: `10.0.2.15/24`
- 仮想ゲートウェイ: `10.0.2.2`
- 仮想 DNS: `10.0.2.3`
- パケットトランスポート: `ws://127.0.0.1:8787/v1/connect`

macOS 用のボードを選び、通常の手順で進めます。

```sh
cargo board select local-macos
cargo build
BARRACUDA_VIRTUAL_IO_ADDR=127.0.0.1:7878 cargo run
```

`BARRACUDA_VIRTUAL_IO_ADDR` は必須です。仮想ペリフェラルマネージャーが待ち受けるループバックアドレスを指定します（ゲートウェイの 8787 以外の空いているポートなら何でも構いません）。`local-macos` は仮想ピン `vio-0` から `vio-7` と、2 つの仮想 I2C コントローラーを公開します。[`platforms/virtual-io`](/platforms/virtual-io) を参照してください。

`cargo run` はプラットフォームのランチャーをビルドし、選択した System イメージを配置し、ループバックのネットワークゲートウェイを起動してから、System アプリケーションを起動します。ランチャーが両方のプロセスを管理するので、Ctrl-C または SIGTERM で実行全体が停止します。2 つ目のターミナルや、ゲートウェイを手動で起動するコマンドは必要ありません。

ゲートウェイは、デバイスから発信された TCP と UDP を通常のホストソケット経由で転送し、`10.0.2.3` 宛ての DNS リクエストを変換し、設定されたゲストの TCP ポートにループバック URL を割り当てます。macOS プラットフォームはセッション開始時にその URL をログに出力し、`.barracuda/address` に書き出します。CLI はこのファイルから現在のアドレスを見つけるので、一時的なループバックポートをローカル設定にコピーする必要はありません。CLI の Local/Remote セレクターは、接続前に見つけた Local アドレスを表示します。`cargo cli configure` も同じセレクターを使い、現在の System のプラグイン設定ポータルを開きます。

プラットフォーム、System、Core、プラグインのログは、`info` レベルで標準エラー出力に書き出されます。ビルドごとに別のレベルを選ぶには、たとえば `BARRACUDA_LOG_LEVEL=debug cargo run` のようにします。
