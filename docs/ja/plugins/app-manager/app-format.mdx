ここでは、アプリコンテナの形式（バージョン 1）を説明します。`app-manager` プラグインは、この形式のコンテナをそれぞれの置き場所から読み込みます。そのため、イメージのビルド、ポータル、Agent のどれが書いたコンテナも同じものです。置き場所によってアプリの種類が決まります（[デバイス UI](/ja/architecture/device-ui) を参照）。以下のマニフェストのルールを機械可読な形にしたものが `crates/appkit/resources/app-manifest.json` です。アプリが何を使えるか、そしてデバイスがアプリとの適合をどう判断するかは App API で定められており、[App API](/ja/plugins/app-manager/app-api) に記載されています。

## 置き場所

| 置き場所    | ディレクトリ                     | 書き込むもの                            | 内容 |
| ----------- | ----------------------------- | ------------------------------------- | ----- |
| `builtin`   | 同梱するプラグインの `/resources/app/` | イメージのビルド（読み取り専用） | システムアプリ |
| `installed` | `/media/apps/<id>/`           | インストール時の `app-manager` プラグイン（非公開） | インストール可能なアプリ |
| `workspace` | `/workspace/media/apps/<id>/` または `<id>.bapp` | ポータル、Agent、その他のプラグイン（共有の Workspace） | インストール用に提示されたアプリ |

組み込みアプリのプラグインは自身のファイルシステムを `app-manager` プラグインに渡し、残りの 2 つは `app-manager` プラグイン自身のスコープにあります。Workspace は読み取るだけです。組み込みアプリとインストール済みのアプリは起動できますが、Workspace のコンテナは提示にすぎません。インストールすると、マニフェストとそこに記載されたファイルが `/media/apps/<id>/` にコピーされ、別のバージョンのインストール済みアプリは置き換えられます。システムアプリの ID はそのアプリ専用です。他の場所にあるコンテナはその ID を使えず、使っている場合は `app.list` が無効として報告します。

## コンテナ

コンテナは、アプリ ID を名前とするディレクトリで、マニフェストとそこに記載されたファイルを並べて置きます。

```text
<id>/
  app.json          the manifest
  main.lua          the entry program (or the file `entry` names)
  view.bvir         optional view program        ┐
  styles.bin        its compiled stylesheet      ├ named by `view`
  font-1.bin …      its baked font atlases       ┘
```

それ以外のファイルは無視されます。名前が `.` で始まるディレクトリはスキップされます。

## パッケージ

Workspace では、アプリを 1 つのファイル `/workspace/media/apps/<id>.bapp` として提示することもできます。このファイルは同じファイル群を含み、署名することもできます。同じ ID がディレクトリとパッケージの両方で提示されている場合は無効です。パッケージは `resources/pack-app.ts` で作成します。

```sh
bun resources/pack-app.ts --new-key key.jwk                 # once, and keep it
bun resources/pack-app.ts <bundle> <id>.bapp --key key.jwk  # sign a built container
bun resources/pack-app.ts <bundle> <id>.bapp                # or leave it unsigned
```

数値はすべてリトルエンディアンです。

| オフセット | サイズ | 内容 |
| --- | --- | --- |
| 0 | 4 | `BAPP` |
| 4 | 1 | 形式のバージョン（1） |
| 5 | 1 | ファイル数（1〜64） |
| 6 | 1 | フラグ: ビット 0 は署名ブロックが続くことを示します |
| 7 | 1 | 0 |
| 8 | 4 | コンテンツの長さ（このヘッダー、ディレクトリ、ファイルの合計） |
| 12 | ファイルごとに 40 | ディレクトリ: 32 バイトまで NUL で埋めたファイル名と、そのオフセットと長さ（各 4 バイト） |
| … | | ファイル本体。それぞれエントリーが示す位置にあります |
| コンテンツの長さ | 133 | 署名付きの場合: `BSIG`、SEC1 非圧縮形式の P-256 公開鍵（65 バイト）、SHA-256 を使ったコンテンツに対する ECDSA 署名（`r ‖ s`、64 バイト） |

一覧表示ではヘッダーとディレクトリだけを読み取ります。インストールが要求されると、デバイスはコンテンツの SHA-256 ハッシュを計算して署名を検証します。署名の検証に失敗したパッケージは無効です。インストール画面は、署名付きパッケージの署名者を鍵の SHA-256 の先頭バイトで表示するか、署名がないことを表示します。インストールされるのは、利用者に表示されたものとまったく同じです。ダイジェストが固定され、その後に変更された提示には `Changed` が返ります。ディレクトリの提示も、ファイルの SHA-256 によって同じように固定されます。

署名付きパッケージからインストールしたアプリは、署名者の鍵をコンテナの隣に保持し、以降はその鍵で署名されたパッケージだけを受け付けます。別の鍵のパッケージ、署名のないパッケージ、ディレクトリは更新として扱われず、その理由が表示されます。署名なしでインストールしたアプリは、どの更新も受け付けます。

## マニフェスト

```json
{
  "format": 1,
  "id": "counter",
  "name": "Counter",
  "version": "0.1.0",
  "api": 1,
  "requires": ["notify@2"],
  "entry": "main.lua",
  "view": {
    "program": "view.bvir",
    "styles": "styles.bin",
    "fonts": ["font-1.bin", "font-2.bin", "font-12.bin"],
    "size": [360, 360],
    "shape": "round"
  }
}
```

| フィールド          | 必須 | ルール                                                        |
| -------------- | -------- | ----------------------------------------------------------- |
| `format`       | はい      | `1`                                                         |
| `id`           | はい      | `a-z`、`0-9`、`-` からなる 1〜32 文字。ディレクトリ名と一致すること      |
| `name`         | はい      | 表示名。1〜64 文字                               |
| `version`      | はい      | 作成者が付けるバージョン文字列。1〜32 文字                |
| `icon`         | いいえ       | ランチャーに表示するシステムアイコンの名前（`lamp` など）。省略すると名前の最初の文字を表示します |
| `entry`        | いいえ       | 実行する Lua プログラム。既定は `main.lua`              |
| `view`         | いいえ       | ヘッドレスアプリでは省略します                                     |
| `view.program` | ビューがある場合 | BVIR のビュープログラム                                      |
| `view.styles`  | ビューがある場合 | コンパイル済みのスタイルシート                                    |
| `view.fonts`   | いいえ       | 組み込み済みのフォントアトラス（最大 16 個）。既定はなし               |
| `view.size`    | いいえ       | `[width, height]`。ビューが収まる最小のディスプレイ。ビルドが `pocket.json` から書き込みます。ビューはディスプレイのサイズでレイアウトされます |
| `view.shape`   | いいえ       | `round` は内接円の中に収まり、どのディスプレイにも合うビュー。`rect` は長方形のディスプレイを必要とするビュー |
| `api`          | いいえ       | アプリが対象とする `app` パッケージのバージョン。既定は `1` |
| `requires`     | いいえ       | アプリの動作に不可欠な安定パッケージ（最大 16 個）。それぞれ `name`、または必要な最低バージョンを付けた `name@version` で記述します |
| `uses`         | いいえ       | デバイスにあれば使う安定パッケージ（最大 16 個）。書き方は `requires` と同じです |
| `permissions`  | いいえ       | その他の Lua パッケージ（最大 16 個）。ボード固有のものと、何も約束しないもの |
| `boards`       | ボード固有のパッケージがある場合 | アプリの対象となるボード。安定した名前で指定します |

記載するファイルはすべて、コンテナ内の単純なファイル名でなければなりません。`A-Z`、`a-z`、`0-9`、`_`、`.`、`-` からなる 1〜64 文字で、`.` や `..` は使えず、ファイルが実在する必要があります。未知のフィールドは拒否されるので、タイプミスは無視されずに報告されます。マニフェストは最大 4 KiB、エントリープログラムは最大 64 KiB、ビューのファイルは合計で最大 512 KiB です。

各パッケージは、`requires`、`uses`、`permissions` のいずれか 1 か所にだけ記載します。安定パッケージは最初の 2 つに、それ以外は 3 つ目に記載します。すべてのアプリが持つアンビエントのパッケージは、どこにも記載しません。`boards` のないボード固有のパッケージは無効です。パッケージが安定、アンビエント、ボード固有のどれかは、マニフェストを読むデバイス上でそのパッケージが宣言する内容（`LuaPackage::interface`）で決まります。そのため、デバイスにないパッケージは、アプリをインストールするデバイスがチェックします。

インストール可能なアプリの実行では、アンビエントのパッケージと、マニフェストで指定したパッケージを `require` できます。指定していないパッケージは存在せず、`require` は失敗します。利用者がアプリをインストールする前に、インストール画面は、アプリが要求する内容を各パッケージのプラグインが宣言した言葉で一覧表示するか、このデバイスで動かせない理由を表示します（[App API](/ja/plugins/app-manager/app-api)）。システムアプリは登録されたすべてのパッケージを `require` できるので、マニフェストに記載する必要はありません。`settings` のような組み込みアプリ自身のパッケージは組み込みアプリ専用で、それを要求するインストール可能なアプリは無効です。

ルールに違反したコンテナは起動できません。`app.list` はそれを `invalid` の下に、置き場所、ディレクトリ名、問題点とともに報告します。たとえば `app.json: JSON schema validation failed at $.view.program: Pattern` のようになります。

## プログラム

エントリープログラムは、他の Lua の実行と同じように VM 上で動き、`app` パッケージがこのアプリに結び付けられます。この結び付けはプログラムの 1 行目を共有するので、エラーの行番号はファイルと一致します。アプリには標準入力がなく、読み取ると EOF が返ります。

### イベントループ

どのアプリも、`app.events()` を回す 1 つのループです。ビューからの呼び出し、ライフサイクルのイベント、タイマーのティックが、その 1 つのストリームに順番に届きます。

```lua
local app = require("app")
local view = app.view()                -- nil for a headless app

for event, a, b in app.events() do
  if event == "app:background" then save()
  elseif event == "app:terminate" then save() break
  elseif event == "increment" then ...  -- a view call: handler name, then arguments
  end
end
```

| イベント            | タイミング                                                                 |
| ---------------- | -------------------------------------------------------------------- |
| `app:active`     | アプリが前面にあり、入力を受け付けます。ビューを持つアプリの最初のイベントです。 |
| `app:inactive`   | 表示されたままですが、入力を受け付けません。オーバーレイに覆われているか、トランジションの最中です。`app:active` まではビューからの呼び出しは来ません。 |
| `app:background` | 前面から外れました。ここで保存してください。サスペンドしたアプリは、別のイベントなしに終了されることがあります。 |
| `app:foreground` | バックグラウンドから戻りました。続いて `app:active` が届きます。              |
| `app:terminate`  | 終了を求められています。猶予期間内に戻らないとキャンセルされます。 |
| `app:tick`       | `app.events{ every = ms }` で設定した間隔（最低 100 ms）が経過しました。バックグラウンドやサスペンド中には届きません。 |
| `app:back`       | アプリが `app.navigation` で最初より深いページにいると報告している間に、利用者が戻るスワイプをしました。前のページを表示し、その深さを報告してください。 |

`app:background` の後、プログラムは猶予期間（1 秒）内に `app.events()` に戻る必要があります。戻るとサスペンドされ、CPU を使わなくなり、ビューツリーは解放されて、復帰時に値から再構築されます。猶予期間が終わってもまだ処理中のプログラムはキャンセルされます。`app:terminate` を無視したプログラムも同様です。ループは `app.exit()` の後に終わり、その後プログラムは戻ります。

ヘッドレスアプリは前面に出ることがありません。サービスとして動き、`app:tick` と `app:terminate` だけを受け取ります。

### API

| 呼び出し | 結果 |
| ---- | ------ |
| `app.id`、`app.name`、`app.version` | マニフェストの値です。 |
| `app.device()` | `app` パッケージのバージョン、ボード、ディスプレイ、タッチ、安定パッケージとそのバージョンです（[App API](/ja/plugins/app-manager/app-api)）。 |
| `app.view()` | ビュー。ヘッドレスアプリでは `nil` です。 |
| `app.events([{ every = ms }])` | イベントのイテレーター。`every` を指定するとタイマーが始まります。 |
| `app.exit()` | イベントループを終了します。 |
| `app.navigation(depth)` | アプリが何ページ目の深さにいるかを報告します。既定の 0 が最初のページです。0 より大きい間は戻るスワイプで `app:back` が届き、0 のときはアプリはそのままです。 |
| `view:set(name, value)` | ビューの `app.d.ts` が宣言した値を書き込みます。型に対してチェックされます。 |
| `view:is_open()`、`view:close()` | ビューの状態です。閉じるとビューからの呼び出しが終わります。 |
| `app.kv.get(key)` | 保存された値、または `nil` です。 |
| `app.kv.set(key, value)` | 真偽値、数値、文字列、および配列または文字列キーを持つテーブルを保存します。`nil` を渡すと削除します。 |
| `app.kv.delete(key)`、`app.kv.keys()` | キーを削除します。キーをソートして一覧表示します。 |
| `app.fs.read(path)`、`app.fs.write(path, data)`、`app.fs.append(path, data)` | ファイル全体へのアクセスです。書き込みはアトミックに置き換えます。 |
| `app.fs.list([dir])` | ソートされた名前です。ディレクトリは `/` で終わります。 |
| `app.fs.exists(path)`、`app.fs.remove(path)`、`app.fs.mkdir(path)` | 基本的なファイル管理です。 |

失敗した場合は例外を発生させず、`nil` とメッセージを返すので、`assert(...)` でエラーに変換できます。キーは 1〜64 バイトで、ストアには最大 16 KiB の JSON を保存できます。ファイルは最大 64 KiB で、パスはアプリ自身のファイルツリーからの相対パスです。深さは最大 8 階層で、`.` や `..` は使えません。

ストレージはコンテナではなくアプリ ID に属します。App Manager の非公開の `/media/data/<id>/`（`kv.json` と `files/`）に置かれ、更新や再起動を経ても残り、他のアプリからは見えません。

## ビュー

`view.program`、`view.styles`、`view.fonts`、`view.size` はビルドの成果物です。MicroTS コンパイラーが `app.tsx` とその `app.d.ts` の契約を View IR に変換し、`ui-link` がそれを BVIR にリンクし、フォントベイカーがアトラスを生成します。ソースのマニフェストの `view` には `shape` だけを書きます。このツールチェーンを実行できない Agent は、ヘッドレスアプリを書くか、既存のビルドのビューファイルを自分のエントリープログラムの隣にコピーします。

## 例: Agent が提示できるヘッドレスアプリ

`/workspace/media/apps/hello/app.json`:

```json
{ "format": 1, "id": "hello", "name": "Hello", "version": "1" }
```

`/workspace/media/apps/hello/main.lua`:

```lua
local app = require("app")
local runs = (app.kv.get("runs") or 0) + 1
assert(app.kv.set("runs", runs))
print("hello from " .. app.id .. ", run " .. runs)
```

`app.install` と `{"id":"hello"}` で提示すると、デバイスにインストール画面が表示されます。利用者がインストールしたら、`app.open` と `{"id":"hello"}` で開きます。すると `app.status` に、`last_exit.output` として `["hello from hello, run 1"]` が表示されます。`crates/appkit/tests/fixtures/` には、ビューを持つビルド済みのサンプルアプリがあり、それぞれ `/workspace/media/apps/<id>/` にそのままコピーできます。`air`（空気質アプリ、パッケージなし）、`lamp`（ライトストリップアプリ、`light` が必須）、`camera`（カメラアプリ、`camera` が必須）、`counter`（カウンター、パッケージなし）です。
