Espressif chips run Barracuda on five bare-metal Platforms, one per chip. They
share a flash tool, `espflash`, and a flash layout, an ESP-IDF partition table in
each Board's `partitions.csv`. They differ in Rust target and toolchain: `esp` is
Espressif's Rust toolchain, and RISC-V GCC is Espressif's `riscv32-esp-elf` GCC.

| Chip (Platform) | Rust target | Toolchain | Boards |
| --- | --- | --- | --- |
| ESP32 (`esp32`) | `xtensa-esp32-none-elf` | `esp` 1.98.1.0 | 24 |
| ESP32-S3 (`esp32s3`) | `xtensa-esp32s3-none-elf` | `esp` 1.98.1.0 | 36 |
| ESP32-C3 (`esp32c3`) | `riscv32imc-unknown-none-elf` | Rust 1.98.1, RISC-V GCC | 5 |
| ESP32-C6 (`esp32c6`) | `riscv32imac-unknown-none-elf` | Rust 1.98.1, RISC-V GCC | 5 |
| ESP32-P4 (`esp32p4`) | `riscv32imafc-unknown-none-elf` | `esp` 1.98.1.0, RISC-V GCC | 7 |

## Install the toolchain

Install `espup` once, then the toolchain for your chip. `cargo board select`
prints the same command when the toolchain is missing.

<Tabs>
  <Tab title="ESP32, ESP32-S3">
    ```bash terminal
    cargo install espup
    espup install --toolchain-version 1.98.1.0
    ```
  </Tab>
  <Tab title="ESP32-C3, ESP32-C6">
    ```bash terminal
    rustup toolchain install 1.98.1
    cargo install espup
    espup install --stable-version 1.98.1 --targets esp32c3 --esp-riscv-gcc
    ```

    For ESP32-C6, use `--targets esp32c6`.
  </Tab>
  <Tab title="ESP32-P4">
    ```bash terminal
    cargo install espup
    espup install --toolchain-version 1.98.1.0 --targets esp32s3,esp32p4 --esp-riscv-gcc
    ```

    `espup` installs the `esp` toolchain beside an Xtensa target, so the
    command names `esp32s3` too.
  </Tab>
</Tabs>

`espup` writes `~/export-esp.sh`. Board selection imports it, so you do not
source it yourself. Install `espflash` to flash:

```bash terminal
cargo install espflash
```

<Note>
  The ESP32-S3 Platform stays on `esp` 1.98.1.0: version 1.99.0.0 reorders
  esp-hal's startup code so that release builds no longer link.
</Note>

## Build, flash, and run

```bash terminal
cargo board select m5stack-cores3
cargo run
cargo image deploy
```

- `cargo run` builds the firmware with `--release`, flashes it with
  `espflash flash --monitor`, and keeps the serial log in the terminal.
- `cargo image deploy` builds the Plugin resource image and writes it to the
  `resources` partition with `espflash write-bin`.

A [release](/contributing/releases) ships each ESP Board as `firmware.bin`, the
bootloader, partition table and app merged from `0x0`, beside
`resources.img`. The browser [installer](/get-started/installation) writes
both; to write them yourself, run `espflash write-bin` with each part's offset
from `manifest.json`.

## Hardware the Platforms drive

Every ESP32 Platform provides digital inputs and outputs, GPIO, SPI devices,
SPI buses, SPI outputs, and I2C devices. Runtime I/O lets Lua scripts claim
these controllers on a Board's exposed pins:

| Platform | I2C | SPI | UART | ADC |
| --- | --- | --- | --- | --- |
| `esp32` | `I2C0`, `I2C1` | `SPI2`, `SPI3` | `UART1` | `ADC1` |
| `esp32s3` | `I2C0`, `I2C1` | `SPI2`, `SPI3` | `UART1` | `ADC1` |
| `esp32p4` | `I2C0`, `I2C1` | `SPI2`, `SPI3` | `UART1` | none |
| `esp32c3` | `I2C0` | `SPI2` | `UART1` | `ADC1` |
| `esp32c6` | `I2C0` | `SPI2` | `UART1` | `ADC1` |

ESP32-S3 adds quad SPI devices, SD/MMC cards, camera capture, an 8-bit
parallel output (`parallel-output`, the LCD_CAM controller in i8080 mode, with
or without a data/command line), I2S audio streams, and capacitive touch.

ESP32-P4 adds I2S audio streams (`i2s-stream`, through the same adapter as
the ESP32-S3) and the MIPI DSI host (`dsi-host`): the link, the RGB565
framebuffer in PSRAM that VDMA scans out, DCS commands before and during
video, and the backlight pin, which it switches on and off because esp-hal has
no LEDC driver for the ESP32-P4.

The ESP32-P4 also drives a microSD card (`sdmmc-device`) on slot 0 of its one
SD host. That slot's fixed pads are `GPIO39` to `GPIO44`, powered from the
chip's LDO VO4 at 3.3 V, so a Board's card declares `slot: 0`,
`power-channel: 4`, and `power-millivolts: 3300`. The Platform owns the SD
host: at startup it builds the host once, keeps slot 1 for a Wi-Fi
co-processor, and hands slot 0 to the Board's card. `cargo board select`
refuses a card on slot 1, or on the slot a Board's co-processor uses. The card
runs on four lines at its `frequency-hz`, switched to high speed above 25 MHz,
and at most 40 MHz. It and the co-processor take turns on the SD host's one
transfer engine in the order they ask, with no priority between them. One
card transfer moves at most 4 KiB, so a large file never holds Wi-Fi up for
longer than one such transfer, about 0.2 ms at 40 MHz.

The ESP32-P4 has no radio. Its IP stack runs on whichever network link the
Board declares:

- **Wired Ethernet**, under `hardware.ethernet`: the EMAC on the Board's RMII
  pins, an IEEE 802.3 PHY at its address, and a DHCP client.
- **A Wi-Fi co-processor**, under `hardware.wifi-coprocessor`: an ESP32-C6
  running ESP-Hosted-MCU on SD host slot 1, beside the Board's microSD card on
  slot 0 if it has one. At startup the Platform switches
  on the co-processor's power if the Board declares a switch, resets it, and
  checks the INIT event its firmware sends. It logs the firmware version when
  the firmware reports one. A wrong chip, firmware without Wi-Fi, another RPC
  version, or an SDIO transfer layout this host does not implement stops the
  co-processor and logs `Wi-Fi is unavailable: <reason>`. The Wi-Fi Plugin
  then sees no Wi-Fi capabilities. Otherwise the co-processor provides a
  station, scanning, and the setup access point.
- **Both**: one IP stack that uses Ethernet while its link is up and the
  Wi-Fi station otherwise. It restarts DHCP on every switch. The setup access
  point is a second stack on the co-processor.

On a Board with neither, the stack has no link and the Wi-Fi Plugin opens no
setup hotspot.

The ESP32-P4's entropy is its random number generator fed by SAR ADC noise,
started the way ESP-IDF starts it on this radio-less chip: at startup the
Platform sets SAR ADC1 sampling an internal channel under the digital
controller and keeps it running. On chip revision v3.0 and later it also
starts the LP_TRNG block and reads it, as ESP-IDF does. Each random byte folds
the generator's output over at least 16 µs. SAR ADC1 then belongs to the
entropy source, so the ESP32-P4 has no runtime ADC. The IP stacks seed their
sequence numbers from the chip's base MAC.
