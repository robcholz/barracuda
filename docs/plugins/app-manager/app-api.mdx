The app API is what an installable app can count on from one device to the
next: the Lua packages it may use, what it may ask the device, and the rules
that keep both stable. It has two parts. The `app` package, this Plugin's,
has a version, the **API level**; this system implements level 1, and an app
names the level it is written for in its manifest's `api` (see
[App format](/plugins/app-manager/app-format)). Every other package is whatever the
device registers, each saying what it promises.

System apps are not bound by the app API: they ship in the image and may
`require` every package.

## Packages

A Plugin that registers a Lua package declares what it promises with
`LuaPackage::interface`, and the app info screen's line for it. This Plugin
reads those declarations from the `LuaPackageRegistry`; it names no other
Plugin's package, so what a device offers apps is exactly what its enabled
Plugins register. Each package's own Plugin documents its functions and the
version each arrived in.

| Interface | How an app gets it | Same on every device |
| --- | --- | --- |
| Ambient | always, without asking | yes |
| Stable, with a version | `requires` or `uses` in the manifest, as `name` or `name@version` | yes, where the device has it |
| Board-specific | `permissions`, with `boards` | no: it talks to one Board's hardware |
| None | `permissions` | no promise |

A package that needs a Board device declares nothing while the Board lacks
the device, so on such a Board an app that requires it does not run.

This Plugin's own packages:

| Package | Interface | Lua API |
| --- | --- | --- |
| `app` | ambient, version 1 | the app itself: events, view, storage, `app.device()` ([App format](/plugins/app-manager/app-format#api)) |
| `notify` | stable, version 2 | `notify.post`, `notify.ask` (below) |

### `notify`

- `notify.post(title [, body]) -> id` adds a notice to the notification
  center.
- `notify.ask(title [, body [, allow, deny]]) -> allowed` asks the person on
  a card listed before every notice and waits for the answer: `true` when
  they allow it, `false` when they deny or dismiss it. From version 2,
  `allow` and `deny` name the card's two buttons (**Allow** and **Deny**
  unless given, at most 6 characters each), as in
  `notify.ask("Lights on?", nil, "Now", "Later")`.

Failures return `nil` and a message.

## Compatibility check

The system checks every installable app against the device, in this order,
and stops at the first reason. `app.list` reports the reason
as the app's `incompatible`; the launcher dims the app and its info screen
shows the reason; `app.open` answers `{"error": "incompatible", "reason": …}`.

| Check | What the reason says |
| --- | --- |
| `api` is above the device's level | `Needs system update (API 2, device has 1)` |
| `boards` does not list this Board | `Only for espressif-esp-vocat-v1-2` (the listed Boards) |
| the app has a view and the device no display | `This device has no display` |
| the view was built for another display than `view.target` | `Built for 320×240 display (device has 360×360)` |
| the display is smaller than `view.size` | `Display too small (needs 480×480)` |
| a package in `requires` is not a stable package here | `This device has no notify` |
| its version here is below the one `requires` names | `Needs system update (notify v2, device has v1)` |
| a package in `permissions` is missing | `This device doesn't support serial` |

An app that does not fit never opens, including one that stops fitting
after a Board or system change.

### Views and the display

A view is laid out at the display's size in view pixels, from 135 px wide to
360 × 360 and more, so write it like a responsive web page:

- Fill the display with `w-full h-full` and lay content out with flexbox,
  not absolute positions or fixed offsets.
- Give content `w-full max-w-[256px]` rather than a fixed width: as wide as
  the display allows, up to the width the design draws it at.
- Text wraps between words to the room it has, as on a web page. Text beside
  other items in a row takes the room they leave with `flex-1 min-w-0`, or
  `basis-[72px] grow min-w-0` to move to its own line when even that is too
  narrow.
- Let rows `flex-wrap`, so their items move to the next line on a narrow
  display.
- Center a column with a `flex-1 min-h-0` spacer above and below its content:
  on a short display the spacers give way first and the bottom is cut, not
  the title.

Fixed sizes stay as written. `view.size` is the smallest display the view
still fits. The device judges a view by its size alone: whether the
display is round or rectangular is for the view's design to handle, so a view
meant for every device keeps its content where a round display shows it.
Text keeps its size: font slots are baked at fixed sizes in view pixels. A
Board may draw each view pixel as several display pixels, its density: a
720 × 720 panel at density 2 shows views at 360 × 360, drawn sharper, so a
view sees the same size on it as on a 360 × 360 panel. A view that needs the
display's size reads it from `app.device().display`. A view built for one
display ([App format](/plugins/app-manager/app-format#building-for-a-display))
runs only on that display.

## Runs

A run of an installable app may `require` the ambient packages and every
package its manifest names in `requires`, `uses`, and `permissions`. A
package the app did not name is not there, and `require` fails. A package in
`uses` may be missing or older than the app would like: check
`app.device().capabilities` before requiring it, or call
`pcall(require, name)`.

`app.device()` describes the device; `capabilities` maps each stable package
to its version:

```lua
{
  api = 1,
  board = "espressif-esp-vocat-v1-2",
  display = { width = 360, height = 360, density = 1 },  -- nil without one
  touch = true,
  capabilities = { notify = 2, ... },
}
```

## Versioning

- A stable package's interface never changes once it is declared: no
  function is removed, renamed, or given other arguments or results.
- Adding functions raises the package's version; its Plugin documents what
  each version added.
- An incompatible change is a new package with a new name; the old one
  stays.
- The `app` package follows the same rules with the API level as its
  version.
- A Board-specific package, or one that promises nothing, may change with any
  system update; that is why apps that use them name their Boards.
