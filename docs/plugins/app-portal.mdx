Adds the Apps page to the portal: the install waiting for the person, with
what it asks for and who signed it, and the apps the Workspace offers. Only
a client on the device's setup hotspot may install or decline, so a Board
without a display installs apps from a phone next to the device. The page
also takes an app from Live Editor, which opens it in a window and sends the
app's package there; see [Live Editor](#live-editor).

- Plugin ID: `app-portal`
- Dependencies: `app-manager`, `webserver`, `captive-portal`, `wifi`
- Settings: none
- Context resources: none
- Provided capabilities: none
- Required capabilities: `AppManager` from `app-manager`, `WebServer` from
  `webserver`, `CaptivePortal` from `captive-portal`
- Workflow: none
- Agent Tools: none
- Lua packages: none
- Web: the `apps` portal entry, and the routes below
- Tasks: none
- Storage: the page in `/resources`

The entry's status is "Waiting" with the app's name while an install waits
(`AppManager::install_request`), else "Nothing waiting".

## HTTP API

| Route | Does |
| --- | --- |
| `GET /api/apps` | `{"waiting": {id, name, version, digest, signer, asks} \| null, "offers": [{id, name, version, incompatible?}], "installed": [{id, version}], "hotspot"}`; `asks` are the install screen's lines (`AppManager::asks`), `installed` the installed apps (not system apps), and `hotspot` whether this request came over the setup hotspot |
| `POST /api/apps/request` `{"id"}` | asks to install an offer (`AppManager::request_install`), which then waits; `204`, or `409 incompatible` with the reason as `message` |
| `POST /api/apps/install` `{"id", "digest"}` | installs the waiting app when `id` and `digest` are the ones waiting, so the install takes what the page showed (`409 changed` otherwise); answers the installed `{id, name, version}` |
| `POST /api/apps/decline` `{"id"}` | declines the waiting app; `204` |
| `PUT /api/apps/offer/<id>` with a `.bapp` body | offers the package in the Workspace as `<id>.bapp`, replacing an older one, and asks to install it (`AppManager::offer_package`); answers `201` with the waiting app as `GET` shows it, `400 invalid_id`, `413 too_large` above 1 MiB, `422 invalid_bundle` for a body that is not a valid package (which is removed again), or `409 incompatible` with the reason |

Install and decline answer `403 setup_hotspot_only` unless the request came
in over the setup hotspot, which `WifiStatus::is_setup_access_point` tells
from the connection's device end (`HttpRequest::local_address`). That keeps the decision with someone in Wi-Fi
range of the device while its hotspot runs, which is while Wi-Fi is not set
up or after the person opens the portal: nobody on the home network or the
internet can install. It is nearness, not identity: the setup hotspot is
open, so anyone in range while it runs can reach the page. Asking works
from any network, like the `app.install` Action, and so does offering a
package. Failures are `{"error", "message"}`, with the message in the
person's words. Off the hotspot, the page shows no install or decline
buttons; it says where to confirm instead.

## Live Editor

Live Editor runs on an HTTPS site, and a browser does not let such a page
call `http://` addresses on the local network. It opens the device's
`/portal/#apps` in a window instead, and the two windows talk with
`postMessage`. The page then calls the device as the portal always does.

1. Opened by another window, the page posts
   `{"type": "barracuda/ready", "v": 1}` to it.
2. Live Editor answers with
   `{"type": "barracuda/offer", "v": 1, "id", "name", "version", "bapp"}`,
   `bapp` being the package's bytes as an `ArrayBuffer` of at most 1 MiB.
   The page takes it only from the window that opened it, and shows that
   window's origin with the app.
3. Nothing reaches the device until the person chooses Send to device.
   The page then sends `PUT /api/apps/offer/<id>`, and the install waits
   for the person at the device like any other.
4. The page reports each step to that origin as
   `{"type": "barracuda/status", "v": 1, "id", "state", "message"?}`,
   `state` being `review`, `sending`, `waiting`, `installed`, `declined`,
   `refused` (the person did not send it) or `failed` (with the device's
   `message`). Once the app no longer waits, `installed` holding it at the
   sent version means it was installed; anything else, that it was declined.

## Building

`resources/web/entry.ts` builds into `filesystem/resources/entry.js` with
the `build` task (`bun ../../tools/web/build.ts`).
