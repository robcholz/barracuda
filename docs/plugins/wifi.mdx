Owns Wi-Fi policy: station and setup access-point lifecycle, persisted station
credentials, and the provisioning page and API.

- Plugin ID: `wifi`
- Dependencies: `webserver`, `captive-portal`
- Settings: none
- Context resources: `wifi` (`take()` of the selected Platform's `WifiDevice`), `ip_stack`
  (the station stack, whose address the Plugin reports; also the access-point stack when no
  radio is present)
- Provided capabilities: `WifiControl`
- Required capabilities: `WebServer` from `webserver`, `CaptivePortal` from `captive-portal`
- Workflow: none
- Agent Tools: none
- Lua packages: none
- Web: portal entry `wifi`, with status; `GET /api/wifi/status`,
  `GET /api/wifi/scan`, `PUT /api/wifi`, `DELETE /api/wifi`; the captive-detection
  paths `/`, `/generate_204`, `/gen_204`, `/hotspot-detect.html`,
  `/library/test/success.html`, `/ncsi.txt`, `/connecttest.txt` and `/fwlink`,
  answered with `CaptivePortal::landing()`; and, when the radio supports an
  access point, a WebServer listener on the access-point stack's port 80
- Tasks: when the Platform supports station configuration, four tasks in the
  `run_wifi_runtime` pool (size 4): the station/AP policy task, the DHCP server
  task, the captive DNS task, and the task that writes the `online` console line
  each time the station gets an address
- Storage: station credentials under the Plugin-scoped KV key `station`; the portal
  files `/resources/entry.js`, `/resources/figure.js` and `/resources/icon.svg`

The Plugin declares a private filesystem, from which its portal entry serves
those bundled files.

Dependent Plugins can require `WifiControl` from `wifi` to inspect support and
state, scan networks, start or stop the access point, configure a persisted
station connection, or forget it and return to the setup AP. The capability
owns these policy transitions, erases the selected Platform's concrete
`WifiDevice` type, and serializes storage and radio operations. The HTTP routes
are adapters over the same capability rather than a separate policy path.
`WifiControl::setup_ssid` names this device's setup access point, and
`WifiControl::station_address` returns the station's IPv4 address while its
network has given it one.

The Plugin owns Wi-Fi policy rather than a specific radio driver. On a managed
embedded Platform it restores persisted station credentials during startup. A
successful restore leaves the device in station mode. Missing or unusable
credentials start the open setup access point at `192.168.4.1/24`;
the Plugin assigns that address to the radio's access-point stack, which the
Platform creates unconfigured. The Plugin then supplies DHCP and captive DNS while the WebServer Plugin serves
the shared route table on AP port 80 with one connection worker.

The setup access point is named `Barracuda-` followed by the last two bytes of
the station MAC in upper-case hex, such as `Barracuda-B2C3`, from
`WifiDevice::station_mac_address`. On an ESP chip that is the chip's base MAC,
the address `esptool` reads while flashing, so a setup tool that flashed the
board knows the name, and boards set up side by side differ. A radio that
reports no MAC names it `Barracuda Setup`.

`GET /api/wifi/status` returns capabilities plus current station and
access-point state; a connected station also carries its IPv4 `address`.
`GET /api/wifi/scan` returns nearby networks. `PUT /api/wifi` validates,
connects, and only then persists `{ "ssid", "password" }`. It answers `200`
with `{ "address", "port" }`: the station's address on the joined network (left
out while it has none) and the portal's port there, `8787`. The setup AP stops
right after that response, so the reply is how a client on the hotspot learns
where the portal went. A failed connection keeps or restores the setup AP so the
caller can retry. `DELETE /api/wifi` removes persisted credentials,
disconnects station mode, and starts the setup AP. `/api/wifi` takes changes
only (`PUT`, `DELETE`); other methods, including `GET`, answer `405`, as do
methods other than `GET` on `/status` and `/scan`.

The Portal registers a Wi-Fi module and exact captive-detection paths used by
common Android, Apple, and Windows clients, which answer with
`CaptivePortal::landing()`. The entry is registered with
`CaptivePortal::register_with_status`; its `GET /portal/status` record maps the
last state `WifiControl::status` observed, without a radio query:

| Last observed state | `state` | `label` | `detail` |
| --- | --- | --- | --- |
| Station connected | `ready` | "Connected" | station SSID, when known |
| Station connecting | `attention` | "Connecting…" | none |
| Disconnected, AP started | `attention` | "Setup hotspot" | AP SSID |
| Disconnected, AP starting | `attention` | "Setup hotspot" | none |
| Disconnected, AP stopped | `off` | "Not connected" | none |

A Platform-managed network reports the host's connection: `ready` "Connected",
without a network name. Credentials are never returned by
the status API or logged. The provisioning API currently has no authentication
or transport encryption; the setup access point is intentionally open, so
provision only in a trusted physical environment.

Host Platforms use `HostWifiDevice`: configuration operations are
unsupported no-ops and station state is already connected because networking
is managed by the host OS. Platforms and Boards without a Wi-Fi radio the
Platform drives, such as an ESP32-P4 Board on wired Ethernet, report a
disconnected `UnavailableWifiDevice` instead of claiming host connectivity; it
refuses to scan, join, or open an access point. Without an access-point
capability the Plugin starts no setup hotspot, DHCP server, or captive DNS,
and `WifiControl::start_access_point` fails with
`WifiControlErrorKind::Unsupported` rather than reporting a hotspot nobody can
join, so the system UI's hotspot tile shows the error. The portal's Wi-Fi
entry reads "Not connected", which is true of Wi-Fi; a wired Board's address
is logged by its Platform when the link comes up.

An ESP32-P4 Board with a Wi-Fi co-processor, such as the M5Stack Tab5,
reports the co-processor's capabilities. They are a station, scanning, and an
access point once the co-processor has started Wi-Fi. They are none when the
co-processor did not start or runs firmware the Platform cannot drive. In that
case the Plugin behaves as on a Board without a radio. See
[ESP32](/platforms/esp32).

The selected ESP32-S3 implementation owns the ESP radio controller and both
Embassy network interfaces. Platform-owned runners drive station DHCP and the
AP stack. The Wi-Fi Plugin owns policy, provisioning services and the AP
address.
Radio state, socket state, futures, locks, and atomics remain in internal RAM.
WebServer TCP and HTTP byte buffers use `BulkBox<[u8]>`, allowing the selected
Platform to place those POD buffers in PSRAM safely.

## Console lines

On a Platform that configures its own station, the Plugin writes one fixed
line to the console at each setup step, for a setup tool attached to the serial
port, such as a web installer that flashed the board over USB:

```text
BARRACUDA wifi=hotspot ip=192.168.4.1 ssid=Barracuda-B2C3
BARRACUDA wifi=connecting ssid=HomeNet
BARRACUDA wifi=failed reason=connection_failed ssid=HomeNet
BARRACUDA wifi=online ip=192.168.1.42 port=8787
```

| Line | Written when |
| --- | --- |
| `hotspot` | An access point starts accepting stations |
| `connecting` | The station starts joining a network, at startup or for `PUT /api/wifi` |
| `failed` | The join failed; `reason` is `invalid_configuration` or `connection_failed`, the codes `PUT /api/wifi` answers with |
| `online` | The station's network gave it an address, each time it does |

Each line starts with `BARRACUDA wifi=`, then `key=value` fields. The `ssid`
field, when present, is the last one and runs to the end of the line, with
control characters removed. A wrong password reports `connection_failed`, like
any other failed join. The lines go through the `log` facade at `info`, so the
Platform's logger prefixes them, and a firmware built with
`BARRACUDA_LOG_LEVEL` below `info` leaves them out.

## Portal page

The `wifi` entry (group Device, order 10) is built on the
portal UI kit from `resources/web/entry.ts`. Its header shows the station
state, network, address and setup-hotspot state from `GET /api/wifi/status`, beside the
`router` figure (`resources/web/figure.js`), whose antennas sweep while
`GET /api/wifi/scan` runs. The page scans on open and on "Rescan", lists
nearby networks strongest first with signal bars and a lock for secured
ones, joins a listed or manually named network with `PUT /api/wifi`, and
offers `DELETE /api/wifi` for the connected network. After an accepted join it
keeps a result card under the header with the portal's address on the joined
network, from the `PUT` reply, as a link: the setup hotspot closes right after
the join, so a phone that joined through it takes the address along. After an
accepted join or forget it calls `context.refreshStatus()`, so the portal's top
bar badge, sidebar and overview follow. Phones get the design's list layout. Results are reported
as portal toasts, in Chinese or English.

Cargo automatically runs the declared `build` task before compiling this
Plugin. To rebuild only the Portal assets, run
`cargo plugin run --plugin wifi build` from the repository root. It writes
`filesystem/resources/entry.js`, `figure.js` and `icon.svg` (the Lucide
`wifi` icon), bundled as the Plugin's private `/resources/` files.
