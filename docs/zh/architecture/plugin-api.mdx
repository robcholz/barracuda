这是编写 Barracuda 插件的权威契约。每个主题都恰好只有一种认可的做法，[`create-plugin`](https://github.com/robcholz/barracuda/blob/master/.agents/skills/create-plugin/SKILL.md) skill 会一步步应用这些规则。与本文不一致的代码属于迁移工作，而不是先例。

## 稳定性

Barracuda 处于 0.x 阶段。Plugin API 可能在任何版本中改变，插件没有兼容层、弃用期或版本检查。

对 Plugin API 的修改作为一个变更集落地：核心、每个受影响的插件、本文、`create-plugin` skill，以及 `cargo plugin sync --check` 的规则一起修改。仓库绝不会处于一部分插件用旧方式、另一部分用新方式的状态。

只有当插件在本仓库之外维护时，兼容性保证才会成为目标。

## 范围

Barracuda 由插件构成，代码归属由两条规则决定。

**被禁用的插件不留任何痕迹**。禁用任何一个插件，它的功能都必须从构建中消失：在该插件以及依赖它的插件之外，没有任何地方提到它，或带有为它准备的代码、配置或文字。

- 核心、System、组合层、平台、开发板、`shared/` 库和应用都与插件无关。它们提供通用机制，永远不为某一个插件提供服务、限制、常量或注释。
- `shared/` 库就是库：它不持有进程范围的服务，由需要该服务的插件来构建它（`http` 插件从 `http-client` 构建请求池；从 `barracuda-tls` 构建 TLS 引擎）。
- 插件之外唯一提到插件的地方，是 `boards/profiles/` 中的开发板 profile 和开发板的 `plugins.<id>` 部分（`cargo plugin sync --check` 会根据每个插件的声明来校验它们），以及注册已启用集合的生成的选择包。

**插件之间只通过能力交互**。一个插件只能通过另一个插件发布的能力类型来使用它，并且只能在把它列入 `depends-on` 之后使用。它绝不深入另一个插件的内部 crate、路由、文件或存储，也绝不揣测一个它不依赖的插件。构建期同样如此：页面只能从它所依赖的插件导入其他插件的 Web 代码。

当某个功能看起来需要在插件之外有一个插件特定的钩子时，这个功能应当放在插件中，而钩子应当放在该插件的能力中。

## 每个主题一种做法

| 主题 | 认可的做法 |
| --- | --- |
| 构造 | `pub fn new(context: &mut PluginContext<Builtins, Io>) -> Self`，别无其他 |
| 平台和开发板资源 | `PluginContext` 的字段，由 System 赋值 |
| 开发板构建哪些插件 | `boards/profiles/` 中的 profile，可由开发板的 `plugins.<id>.enabled` 覆盖 |
| 按开发板的设置 | `plugin.toml` 中的 `[config.<name>]`，在开发板的 `plugins.<id>` 中设置 |
| 开发板外设 | `plugin.toml` 中 `[peripherals.<kind>]` 下的槽位，通过对应的 `config::peripherals` 常量取得 |
| 插件之间的调用 | 类型化能力：提供者中 `provide`，使用者中 `require` |
| HTTP 客户端 | 从 `http` require 的 `http_client::ClientFactory` |
| Workflow 集成 | Workflow Action 或 Event，其 schema 位于 `schemas/` 下 |
| 面向模型的操作 | 适配器插件中的 Agent Tool |
| 面向 Lua 的操作 | 在 `vm` 插件的 `LuaPackageRegistry` 中注册的 Lua 包 |
| 门户页面 | 有状态时用 `CaptivePortal::register_with_status`，没有时用 `register` |
| 插件 HTTP API | 插件自己在 `WebServer` 上的路由；其路径和请求体是插件及其页面私有的 |
| 用户会修改的设置和凭据 | 插件范围的 KV 存储 |
| 文件 | 插件的 `ScopedVfs`，挂载点由文件的生命周期决定 |
| 打包的文件 | `filesystem/resources/` 和 `filesystem/workspace/resources/` |
| 文档 | 文档站点中的 `docs/plugins/<id>.mdx`，按下面的模板编写 |

## 目录布局

框架拥有 `plugins/<id>/` 根目录下的每个名称。插件只使用它需要的条目，不在根目录添加任何其他内容：

```text
plugins/<id>/
├── plugin.toml                    # identity, dependencies, settings, host tasks
├── crates/
│   ├── plugin/                    # package barracuda-<id>-plugin, the entry point
│   │   └── build.rs               # only with settings, peripheral slots, or a build task
│   └── <crate>/                   # optional runtime or domain crates
│       └── resources/tools/<tool>/
│           ├── schema.json        # Agent Tool input schema
│           └── usage.md           # Agent Tool usage text
├── schemas/
│   ├── action/<address>/
│   │   ├── request.json
│   │   └── response.json
│   └── event/<event-id>.json
├── resources/                     # author-owned build inputs, such as web/
└── filesystem/                    # build outputs and assets bundled into the image
    ├── resources/                 # -> the Plugin's /resources
    └── workspace/resources/       # -> the shared /workspace/resources
```

插件的文档和其他页面一起放在文档站点中：

```text
docs/plugins/
├── <id>.mdx                       # required
└── <id>/
    ├── action.mdx                 # required when schemas/action/ exists
    ├── event.mdx                  # required when schemas/event/ exists
    └── <topic>.mdx                # optional, such as http.mdx
```

把每个页面添加到 `docs/docs.json` 中该插件的分类下。

- `crates/plugin` 存放带有 `#[barracuda_plugin::macros::plugin]` 注解的类型及其 `impl Plugin`。只有当某个运行时或领域边界拥有大量状态、多个契约、可复用的 API 或聚焦的测试时，才添加另一个 crate。不要添加只有 schema 或只有传输的 crate。其他插件只使用 `-plugin` crate 的公开项。
- `crates/<crate>/resources/` 下的文件是该 crate 的编译期输入，例如 Agent Tool 定义。它们永远不会被打包。
- `resources/` 存放插件的构建任务转换为 `filesystem/resources/` 的源文件，例如 `resources/web/entry.ts`。作者可以自由组织其内部结构。它与运行时的 `/resources` 挂载点无关。
- `filesystem/` 永远不包含 `data/`、`cache/`、`media/`，也不包含 `workspace/` 下的可变子树。

## `plugin.toml`

`plugin.toml` 是插件身份的唯一来源：

```toml
id = "example"
depends-on = ["webserver", "captive-portal"]
description = "One sentence on what the Plugin owns."
```

ID 和每个 `depends-on` 条目都匹配 `^[a-z0-9]+(?:-[a-z0-9]+)*$`。`depends-on` 直接列出插件使用其能力或 crate 的每个插件；这些插件自身的依赖不重复列出。`plugin` 宏把 ID 和依赖烘焙进 `PluginDeclaration`；Rust 代码永远不重复它们。添加、重命名或删除插件，或者修改它的依赖之后，运行 `cargo plugin sync`。

### 设置

一个在不同开发板之间不同、但在一次构建中固定的值就是设置，例如某块开发板能负担多少个某种连接：

```toml
[config.receive-slots]
type = "usize"
default = 1
description = "Long-lived connections the Plugin holds at once."
```

`type` 是 `bool`、`u8`、`u16`、`u32`、`usize`、`i32` 或 `str` 之一，`default` 必须是该类型的值。开发板在它的 `board.yml` 中覆盖它：

```yaml
plugins:
  example:
    receive-slots: 3
```

`enabled` 和 `peripherals` 是 `plugins.<id>` 的保留键（见“按开发板启用”和“外设”）；设置永远不使用这些名称。

如果开发板设置了其插件未声明的设置，或者值的类型错误，`cargo plugin sync --check` 会拒绝它。插件的 `build.rs` 调用 `barracuda_plugin_build::build()`，crate 把解析出的值作为常量引入，以 SCREAMING_SNAKE_CASE 命名：

```rust,ignore
mod config {
    barracuda_plugin::config!();
}

static BUFFERS: ReceiveBuffers<{ config::RECEIVE_SLOTS }> = ReceiveBuffers::new();
```

设置永远不是平台或开发板的字段，System 也永远不读取它。用户在运行时修改的值不是设置；它存放在 KV 存储中。

### 外设

驱动开发板外设的插件要为它声明一个槽位，每种外设类型一个表，槽位名由插件选择：

```toml
[peripherals.display]
main = "primary"                               # the Board's primary display

[peripherals.touch]
main = { fill = "primary", optional = true }   # starts without touch
```

| 填充 | 槽位得到 |
| --- | --- |
| `"primary"` | 开发板为该类型标记为主设备的设备 |
| `"any"` | 该类型中没有被其他槽位取走的唯一设备 |
| `"*"` | 该类型中所有没有被其他槽位取走的设备，以列表形式 |

除非写明 `optional = true`，槽位都是必需的；`"*"` 槽位总是可选的。插件可以为一种类型声明多个槽位。类型就是 `peripherals/impl/` 中的 `peripheral:` 名称：`display`、`touch`、`buttons`、`indicator`、`led-strip`、`buzzer`、`vibration`、`infrared`、`camera`、`audio-codec`、`inertial-measurement`、`power-monitor` 和 `real-time-clock`。可移动存储由 System 拥有，永远不会被认领。

开发板在 `peripherals.devices` 下提供具名设备，当某种类型有多个设备时把其中一个标记为 `primary: true`，并且只在需要覆盖默认值或消除歧义时才为槽位接线：

```yaml
plugins:
  example:
    peripherals:
      display.main: back-eink
```

每块开发板在构建期解析每个已启用插件的每个槽位：先由接了线的槽位取走它的设备，然后是 `"primary"` 槽位，然后是 `"any"` 槽位，最后某种类型唯一的 `"*"` 槽位按设备名顺序取走剩下的设备。以下情况都会让构建失败：一个设备被取走两次、同一种类型有两个 `"*"` 槽位、`"any"` 槽位有多个候选、必需的槽位为空，或者接线指向未知设备、其他类型的设备或未声明的槽位；错误信息会打印出能解决问题的 `plugins.<id>.peripherals` 行。

插件的 `build.rs` 调用 `barracuda_plugin_build::build()`，`config!()` 在 `config::peripherals` 中为每个槽位定义一个常量，命名为 `<KIND>_<SLOT>`：单个设备是 `Option<Instance>`，`"*"` 则是由设备名和实例组成的 `&[(&str, Instance)]`。插件通过这些常量取得它的设备；它永远不提到某个开发板设备的名字。

### 主机任务

生成文件的插件要声明一个具名的主机任务：

```toml
[tasks.build]
cwd = "."
command = ["bun", "../../tools/web/build.ts"]
inputs = ["resources/web/entry.ts", "../../package.json", "../../bun.lock"]
outputs = ["filesystem/resources/entry.js"]
```

- `cargo plugin run <task>` 按目录顺序为每个拥有该任务的已启用插件运行它，或者用 `--plugin <id>` 只为一个插件运行。
- 资源必须在编译前生成的插件要安装一个调用 `barracuda_plugin_build::build()` 的 `build.rs`；然后 Cargo 会运行它的 `build` 任务，为声明的输入和输出计算指纹，并跳过未改变的工作。输入可以指向共享的源路径，例如它所依赖的另一个插件的 Web 套件；输出和 `cwd` 保持在插件内部。
- 任务以开发者的权限运行受信任的仓库代码，永远不重新进入 Cargo，永远不安装工具，并保持在前台运行。`depends-on` 不是任务图。

前端工具链是整个仓库共用的：一个根目录的 `package.json`、`bun.lock`、TypeScript 配置、格式化工具和 linter（在根目录运行 `bun run format`、`lint`、`check`、`test`）。Web 源文件及其测试留在插件的 `resources/web/` 中；共享的构建器和测试辅助工具位于 `tools/web/`。

## 按开发板启用

固件包含哪些插件是其开发板的属性。`boards/profiles/<name>.yml` 中的 profile 指定一组插件，并且可以扩展其他 profile，一个或一个列表；被引用两次的 profile 只算一次，扩展自身的 profile 会失败：

```yaml
# boards/profiles/gateway.yml
extends: network
enable: [agent, imessage-gateway, imessage-telegram]
```

```yaml
# boards/profiles/screen-offline.yml
extends: [lua, ui]
```

这些 profile 是分层的，从 `minimal`（无网络、无 Lua）到 `screen`；[开发板 profile](/zh/boards/profiles) 列出了它们，并说明该选哪一个。

开发板指定它的 profile（不指定时为 `headless`），并在 `plugins.<id>` 中覆盖单个插件：

```yaml
profile: gateway
plugins:
  imessage-telegram:
    enabled: false
  camera:
    enabled: true
```

启用的集合依次是 profile 链、开发板的覆盖，然后是已启用插件传递依赖的每个插件。如果开发板禁用了它所启用插件的某个依赖，构建会失败；如果某个已启用插件的必需外设槽位无法由开发板填充，也会失败。被忽略的 `.barracuda/disabled-plugins` 文件只在某一位开发者的机器上禁用插件；它也会禁用这些插件的依赖方，sync 会说明这一点。

`cargo board select` 把启用的集合写入 `.barracuda/selection/plugins` 下的本地选择包，System 依赖它来准确注册这些插件。每个插件都保留在 `Cargo.lock` 中，所以切换开发板不会改变任何已提交的文件。

## 构造

每个插件都恰好有这样一个构造函数，System 以 `<Type>::new(&mut plugin_context)` 的形式调用它：

```rust,ignore
impl ExamplePlugin {
    #[must_use]
    pub fn new<Builtins, Io>(context: &mut PluginContext<Builtins, Io>) -> Self {
        let clock = config::peripherals::REAL_TIME_CLOCK_MAIN
            .and_then(|instance| context.hal.peripherals.take_real_time_clock(instance));
        Self { clock }
    }
}
```

- 这个参数是唯一的参数。需要平台或开发板资源的插件从上下文中读取；没有插件特定的参数，生成的注册代码中也没有特例。
- 当 clippy 要求时使用 `const fn`。对其设备类型泛型的插件可以固定 `Io`，或者用 `where` 子句约束 `Builtins`。
- 构造只是把资源从上下文中移出，并用它们构建插件自己的值。它永远不注册、不派生任务，也不触碰存储；这些属于 `register` 和 `start`。
- 插件永远不保存上下文或对它的引用。

`PluginContext` 只携带平台和开发板的原始资源，无论是否有插件使用，它们都存在：

| 字段 | 用法 |
| --- | --- |
| `target_identity` | 复制 |
| `ip_stack` | 复制 |
| `entropy` | 克隆 `SharedEntropy` |
| `wifi` | 由唯一拥有 Wi-Fi 策略的插件 `take()` |
| `hal.peripherals` | 用插件的 `config::peripherals` 常量调用 `take_<peripheral>(instance)` |
| `hal.exposed_io` | 克隆 `Arc` |

新增字段是一次 Plugin API 变更，并且需要一个原始的平台或开发板资源。基于这些资源构建的服务（例如 TLS 或 HTTP 池）由拥有它的插件构建，并作为它的能力发布。

## 生命周期

`Plugin::REQUIREMENTS` 声明插件需要的文件系统：`PluginFilesystem::None`（默认）、`Private` 或 `Inspect`。门户条目、文件存储和打包的资源需要 `Private`。

`Plugin::register` 按依赖顺序同步运行。它：

1. 从 `depends-on` 中列出的插件 require 能力；
2. 构造完整的能力和服务图；
3. 用 `provide` 发布每个提供的能力；
4. 安装 Workflow Action、Agent Tool、Lua 包、门户条目和 HTTP 路由；
5. 用 `context.retain(...)` 让每个注册守卫保持存活。

`Plugin::start` 在所有插件都注册之后运行。它只通过 `context.task_spawner()` 派生长期运行的工作，并给每个常驻任务分配它自己的 `context.task_token()`。它不能发布能力。需要所有插件都已注册的工作（例如加载打包的 Workflow）从这里开始。任务所有权、容量和取消遵循[执行所有权](/zh/architecture/execution-ownership)。

Plugin Manager 拥有回滚和卸载。插件永远不添加自己的生命周期或全局注册表。

## 协作契约

根据调用方选择契约：

| 调用方 | 契约 |
| --- | --- |
| 另一个插件 | 类型化能力 |
| Workflow | Workflow Action，异步事实则用 Workflow Event |
| 模型 | Agent Tool |
| VM 中的 Lua 代码 | Lua 包 |

一项服务可以暴露其中多个视图。类型化能力始终是直接的、面向机器的 API。其他每个视图都是它之上的一层薄适配器，只有提供者能用的修改句柄对提供者保持私有。

### 类型化能力

提供者用 `PluginRegisterContext::provide` 发布 `Rc<T>`。使用者在 `depends-on` 中列出提供者，并用 `require::<T>("<provider-id>")` 获得同一个值。两者之间没有 JSON、字符串查找或运行时发现。

能力是提供者面向其他插件的全部公开接口：使用者调用的方法，以及这些方法接收和返回的类型。当使用者需要提供者拥有的服务（客户端、连接槽位、代为挂载的路由）时，由能力把它交出来；使用者永远不自己构建提供者的服务。

### Workflow Action

Action 实现 `WorkflowActionHandler`，在 `WorkflowActionRegistry` 中注册，并用 `workflow_action_schema!("<address>")` 嵌入它的 schema，该宏读取 `schemas/action/<address>/request.json` 和 `response.json`：

```rust,ignore
impl WorkflowActionHandler for SendMessage {
    type Request = SendRequest;
    type Response = SendResponse;

    const SCHEMA: WorkflowActionSchema = workflow_action_schema!("message.send");

    fn invoke(&self, request: SendRequest) -> WorkflowActionFuture<'_, SendResponse> {
        Box::pin(async move { send(request).await })
    }
}
```

运行时在解码请求之前校验请求，在返回响应之前校验响应。没有返回值的成功是 `{}`。稳定的业务失败是一个普通响应，例如 `{"error":"not_found"}`，并出现在响应 schema 中；`WorkflowActionError` 只用于基础设施失败。

### Workflow Event

Event 类型以一个稳定的 `ID` 实现 `Event`，并通过 `WorkflowService::emit` 发出，当 Topic 参与匹配时则用 `emit_to`。它的载荷是一个有界的 Serde 值，由 `schemas/event/<event-id>.json` 描述。逻辑流是一串 Event，携带关联、顺序和终止结果，其容量和背压由生产者拥有。

连接两个插件的 Workflow 随同时依赖两者的插件一起发布，放在该插件的 `/resources/workflows.json` 中，并在 `start` 中通过 `WorkflowService` 以临时方式加载。

### Agent Tool

Tool 通过 `AgentToolRegistry` 注册。Agent 自身之外的任何 Tool 都放在名为 `agent-<name>` 的适配器插件中，由它把调用转换为提供者的类型化能力或 Workflow 操作，这样提供者在没有 `agent` 时仍然可用。它的定义位于注册它的 crate 旁边，即 `crates/<crate>/resources/tools/<tool>/schema.json` 和 `usage.md`。提示、响应编码和 Tool 错误都留在适配器中，Tool 遵循[面向 Agent 的 API 设计](/zh/architecture/agent-oriented-api-design)。

### Lua 包

VM 内置包之外的 Lua 包，由名为 `vm-<name>` 的插件在从 `vm` require 的 `LuaPackageRegistry` 中注册。丢弃注册会撤销该包的回调，并使它的句柄失效。

包用 `LuaPackage::interface` 说明它承诺了什么：环境的（它不给代码任何可能被滥用的东西）、稳定的（带有一个统计其函数新增次数的版本，以及一行说明代码可以用它做什么的文字），或者开发板特定的；`None` 不承诺任何东西。决定哪些代码获得哪些包的插件从注册表中读取这些信息，并且不提到任何不是它自己注册的包。需要某个开发板设备的包，在开发板缺少该设备时不承诺任何东西。

每次运行的 Lua 堆都容纳内置包、每个已注册的包和脚本。VM 拥有这份预算：它最多容纳 `MAX_LUA_PACKAGES` 个包，并证明内置包、这么多个各自保留 `LUA_PACKAGE_HEAP_BUDGET_BYTES` 的包，再加上一次安装的瞬时峰值 `LUA_PACKAGE_INSTALL_PEAK_BYTES`，仍能给脚本留出它的预留空间。每个包插件的测试都要对它注册的每个包断言 `barracuda_vm_runtime::fits_package_budget(&package)`。这样任何包的组合都能容纳得下，也没有任何测试需要提到另一个包插件。

## 门户和 HTTP

有配置页面的插件向 `CaptivePortal` 注册一个 `WebEntry`：

- 当它的卡片显示状态时，用 `register_with_status(entry, files, || EntryStatus)`。这个闭包是同步且廉价的：它读取插件已经持有的状态，永远不触碰设备或网络，也永远不调用门户。
- 没有状态时，用 `register(entry, files)`。

`files` 是 `ResourceFiles::from(context.filesystem()?.clone())`，从插件的 `/resources` 提供该条目的模块和资源。页面的源文件位于 `resources/web/`，构建到 `filesystem/resources/` 中，它从 `captive-portal` 导入门户 UI 套件，其他 Web 套件只从它所依赖的插件导入。只有在 `context.has(id)` 表明某个条目存在之后，页面才能链接到它。从自己的路由把客户端引导到门户的插件，用 `CaptivePortal::landing()` 应答它们。

插件自己的 HTTP API 用 `WebServer::serve_http` 提供，并像任何注册一样被保留。它的路径、方法和请求体是插件与其页面之间的私有契约，记录在插件页面或它的 `http` 页面上。路由永远不返回凭据。

## 存储和文件

按生命周期而不是大小对状态分类：

| 状态 | 存放位置 |
| --- | --- |
| 设置、凭据和小型结构化状态 | 插件范围的 KV 存储，`context.storage()` |
| 保证正确性所需的文件 | `/data` |
| System 可以删除的可重新生成的文件 | `/cache` |
| 大型持久运行时内容 | `/media` |
| 随镜像发布的文件 | `/resources`，只读 |
| 所有插件共享的不可变文件 | `/workspace/resources`，只读 |
| 一次运行中在插件之间交换的文件 | `/workspace/cache` |
| 比其运行存活更久的共享文件 | `/workspace/media` |
| 当前插入的可移动介质 | `/workspace/removable/<slot-id>` |

例如，打包的模型属于 `/resources`，可以重新下载的模型属于 `/cache`，用户上传的内容属于 `/media`，而交给另一个插件的脚本输出属于 `/workspace/cache`。

插件从 `context.filesystem()` 得到一个普通的 `ScopedVfs`。它永远不挂载、不选择文件系统、不访问 System 路径，也不触碰另一个插件的命名空间，并且永远不直接在 `/` 或 `/workspace` 写入。保证正确性所需的共享状态只有一个所有者，存放在该所有者的 KV 存储或 `/data` 中。

挂载策略强制执行这份契约：在 `/resources` 和 `/workspace/resources` 之下写入会以 `ReadOnly` 失败，跨挂载点重命名会以 `CrossMount` 失败，路径无法逃出范围，卸载会保留 `/data`、`/media` 和 `/workspace/media`。`/cache` 和 `/workspace/cache` 随时可能消失。可变的默认值从 `/resources` 读取，只在 `/data` 中不存在时才复制过去。

打包的文件直接映射：

```text
plugins/<id>/filesystem/resources/index.html
-> /resources/index.html                     (the Plugin's own view)
plugins/<id>/filesystem/workspace/resources/models/common.bin
-> /workspace/resources/models/common.bin   (every Plugin's view)
```

共享的贡献按路径合并，冲突会让镜像构建失败。System 如何支撑这些挂载点，见[平台架构](/zh/architecture/platform-architecture)。

## 测试

测试使用生产 API，并且从不左右它的形态：不存在仅仅为了让测试注入假对象而存在的构造函数、参数、feature 或公开项。插件的测试注册其依赖图中真实的插件，由 `barracuda-platform-test` 替代平台（回环网络、内存 Flash、脚本化的服务器），并用 `rusty_fork_test!` 让每个需要进程范围资源（例如静态大小的缓冲区）的测试在自己的进程中运行。测试可以依赖其插件直接或间接依赖的插件，不能依赖其他插件。

## 插件文档

每个插件都有一个页面 `docs/plugins/<id>.mdx`，格式如下：

````markdown
---
title: "<Name> Plugin"
description: "<One sentence, starting with a verb, on what the reader gets from the Plugin.>"
---

<One or two sentences on what the Plugin owns.>

- Plugin ID: `<id>`
- Dependencies: `<id>`, `<id>`
- Settings: `<name>` (`<type>`, default `<value>`)
- Context resources: `<field>`, peripheral slot `<kind>.<slot>` (`<fill>`)
- Provided capabilities: `<Type>`
- Required capabilities: `<Type>` from `<id>`
- Workflow: Actions `<address>`, see [Actions](/plugins/<id>/action); Events `<event-id>`, see [Events](/plugins/<id>/event)
- Agent Tools: `<tool>`
- Lua packages: `<package>`
- Web: portal entry `<entry-id>`, with status; `GET <path>`, `PUT <path>`
- Tasks: <each owned long-running task and its capacity>
- Storage: <KV keys and file paths>

<Free-form sections, in any order, for everything else.>
````

- 全部十二个条目按此顺序出现在第一个 `##` 标题之前，每个都从行首开始。为空的条目写 `none`。值可以换行到缩进的续行上。
- `Plugin ID` 和 `Dependencies` 与 `plugin.toml` 完全一致，依赖按其中的顺序排列，`Settings` 恰好列出它的 `[config.*]` 设置。
- 只描述当前的契约。历史属于版本控制。

`action` 页面列出每个 Action 地址、它的请求和响应、稳定的业务错误以及 schema 路径。`event` 页面列出每个 Event ID、它的载荷、schema 路径、Topic、发出条件和界限。

页面是 MDX：在正文中把 `<`、`{` 和 `}` 写成 `\<`、`\{` 和 `\}`，或者放在代码片段中。

## 检查

在 CI 中运行的 `cargo plugin sync --check` 会拒绝：

- 插件根目录包含上述布局之外的名称；
- `schemas/` 中除 `action/<address>/{request,response}.json` 和 `event/<event-id>.json` 之外的条目；
- 缺少 `docs/plugins/<id>.mdx`，缺少或错放了摘要条目，或者摘要条目在 ID、依赖或设置上与 `plugin.toml` 不一致；
- 存在对应的 schema 时，缺少 `docs/plugins/<id>/action.mdx` 或 `docs/plugins/<id>/event.mdx`；
- 插件 crate 依赖另一个插件的 crate，却没有把该插件列入 `depends-on`（测试可以使用它传递依赖的插件）；
- 开发板设置了其插件未声明的设置，或者类型错误；
- profile 或开发板指向未知的 profile 或插件、开发板禁用了它所启用插件的某个依赖，以及任何外设槽位无法解析的开发板。

生成的注册代码用 `new(&mut plugin_context)` 构造每个插件，所以其他构造函数会编译失败。检查只覆盖这些形式；上面的范围规则通过评审来保证。
