文档遵循体验阶梯：每位读者从自己项目所需的层级开始，想往上走多远就走多远。每个页面都要写得让处在该层级的读者在第一屏就能动手。

## 页面放在哪里

| 标签页 | 分组 | 放在这里的内容 |
| --- | --- | --- |
| 指南 | 开始 | 欢迎页、安装、快速开始，以及三个概念：体验阶梯、Agent、插件 |
| 指南 | 01 · 使用设备 | 使用运行中的设备：门户、消息通道、脚本、自动化 |
| 指南 | 02 · 配置 | 选择固件中的插件、构建、烧录 |
| 指南 | 03 · 应用 | 为设备构建应用 |
| 开发 | 04 · 插件 | 编写插件和插件契约 |
| 开发 | 05 · 开发板与平台 | 开发板、外设、驱动和平台；在 **平台** 下每个平台系列一个页面（`platforms/<family>.mdx`），在 **开发板** 下每块开发板一个页面，按厂商分组（`boards/supported/<board-id>.mdx`）。添加开发板或平台时，同时添加它的页面 |
| 开发 | 06 · 定制固件 | 让固件适配芯片和预算 |
| 开发 | 参与贡献 | 开发 Barracuda 本身：约定、内部实现、测试、基准、共享 crate、产品文档 |
| 插件 | 按系列 | 每个插件一个页面，位于 `docs/plugins/<id>.mdx`，采用 [Plugin API](/zh/architecture/plugin-api) 要求的格式 |
| 参考 | 参考 | CLI、文件格式和术语表 |
| 更新日志 | — | 无需编写：该标签页、横幅和页脚链接都打开 [GitHub Releases](https://github.com/robcholz/barracuda/releases) |

内部实现放在参与贡献下，绝不放在用户最先阅读的层级中。把每个新页面都加入 `docs/docs.json`，并加到每种语言的导航中。

## 语言

文档有英文和简体中文两种语言。英文是源文本；每个页面都有一份跟随英文的中文副本。

- 页面的中文副本位于 `zh/` 下的相同路径，例如 `zh/get-started/quickstart.mdx`，`docs.json` 中的中文导航在该路径列出它。中文导航中绝不列出英文路径：Mintlify 按路径判断语言，读者会因此进入英文站点。
- 新增或修改英文页面时，在同一个 pull request 中新增或修改它的 `zh/` 副本，并把新页面加到两种语言的导航中。代码、命令、ID 和路径保持完全一致；翻译正文、标题、页面标题和描述。
- 在中文页面中，每个内部链接都带 `/zh` 前缀（`/zh/use/scripts`），且不带 `#锚点`：中文标题的锚点不同。
- 英文是基础语言：英文页面从不出现中文，所有标签都用英文字符串。中文页面可以出现英文。
- 中文页面里，门户上的标签使用代码中的中文字符串，例如 **Models** 写作 **模型配置**；只有英文的标签保持英文，设备上的标签都是这样：设备界面只有英文。
- 中文句末标点放在粗体之外：写 `**依赖**。`，而不是 `**依赖。**`，后者会把星号原样显示出来。

## 每个页面

- **Frontmatter。**`title`，以及一句话的 `description`，最多约 110 个字符。描述以读者视角的动词开头：“用 `gpio` 包从 Lua 读取和驱动开发板的引脚。”
- **标题**。功能页面用名词：“消息通道”“开发板 profile”。命令页面用命令本身：“cargo board”。任务页面用祈使句：“编写插件”。
- **第一屏**。用一两句话说明读者能得到什么，然后给出可以运行或复制的内容及其产生的结果。规则、边界情况和内部实现放在后面。
- **语气**。用“你”称呼读者，用祈使句给出步骤。用 `Steps` 表示一系列步骤，用 `CardGroup` 表示接下来可以去的地方。
- **事实**。每个命令、路径和名称都要对照代码核实。描述现在已有的内容；任何计划中的内容都标注为计划中。
- **MDX**。在正文中把 `<`、`{` 和 `}` 写成 `\<`、`\{` 和 `\}`，或放在代码片段中。带 `href` 的 `Card` 中不放链接。

## 面向每类读者的用词

| 读者 | 部分 | 使用 | 在他们的页面上避免 |
| --- | --- | --- | --- |
| 创客和教育用户 | 开始、01、02 | 安装、与开发板对话、选择插件、设备门户 | `no_std`、执行器、平台契约 |
| 应用开发者 | 03 · 应用 | 应用、屏幕、安装、应用 API | Rust 内部实现 |
| 插件开发者 | 04 · 插件 | 插件、能力、Workflow Action 和 Event、Agent Tool、Lua 包 | — |
| 开发板厂商和贡献者 | 05 · 开发板与平台 | 开发板、平台、外设、驱动、profile | — |
| 构建者 | 06 · 定制固件 | profile、预算、裁剪、适配 | — |
| 开发 Barracuda 的人 | 参与贡献 | 准确的技术术语 | — |

在所有地方都使用[术语表](/zh/product/glossary)中定义的术语：插件、开发板、平台、System、Agent、消息通道。说“板上 Agent”，不说“助手”；说“Lua 脚本”，不要只说“代码”。

## 样式

`style.css` 把 Mintlify 的组件画成 Barracuda design system 里的样子：代码块是它的 Window，提示框是它的 Alert，Steps 用它的步骤标记，卡片以它的图标方块开头，正文链接和行内代码遵循它的 Text。只用它的 token（`--bc-*`）和圆角，不要新增颜色或尺寸。文件顶部的 token 块由 `ui/tokens.css` 生成；token 变了之后，重新生成：

```bash terminal
bun tools/web/docs-tokens.ts
```

token 块过期时，`bun test tools/web` 会失败。
