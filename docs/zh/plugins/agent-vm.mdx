title: "Agent VM 插件"
sidebarTitle: "Agent VM"
description: "让 Agent 用 `vm_run` 工具在后台运行 Lua 脚本。"
---

把 `vm` 插件的 `Vm` 能力作为原生后台工具暴露给 Agent。

- 插件 ID：`agent-vm`
- 依赖：`agent`、`vm`
- 设置：无
- 上下文资源：无
- 提供的能力：无
- 需要的能力：来自 `agent` 的 `AgentToolRegistry`、来自 `vm` 的 `Vm`
- Workflow：无
- Agent Tool：`vm_run`
- Lua 包：无
- Web：无
- 任务：无
- 存储：无

插件注册期间，`agent-vm` 把 `vm_run` 添加到 `AgentToolRegistry`。
`vm_run` 是一个后台工具：它的已接受输出包含 `run_id`，之后这次运行就存在于调用它的 Agent 的后台池中。当 Lua 在
`io.read()` 中阻塞时，它会向 Agent 发送一个非终止的 `{"kind":"input_required","run_id":...}`
进度更新。从后台处理器返回时，会隐式地以按顺序排列的 `print(...)` 输出行和最终结果完成这次调用。

这次运行的 `BackgroundToolControl` 向 `background_list` 报告 `running` 或 `input_required`
状态，并把 `background_input` 作为一个值或 EOF 送给 `io.read()`。没有 VM 专用的列出、输入或取消工具。

Agent 的后台池拥有这次运行的完成 future，而该 future 拥有
`VmRun` 句柄。`background_cancel`、取消或删除该 Agent 都会丢弃这个句柄，从而取消尚未完成的 VM 执行并释放它的运行时槽位。

适配器不拥有任何 VM 运行时或执行状态。每次更新都来自
`Vm` 类型化能力返回的 `VmRun` 句柄；它不会把 VM 状态转换为 Workflow Event。
