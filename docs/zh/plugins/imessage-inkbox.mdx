IMessage Inkbox 插件把 Inkbox 添加为一个 iMessage Gateway 消息通道：它通过 API key 或自助注册配置一个 Inkbox agent，通过 Inkbox API 发送消息，并通过轮询接收消息。

- 插件 ID：`imessage-inkbox`
- 依赖：`imessage-gateway`、`webserver`、`captive-portal`
- 设置：无
- 上下文资源：无
- 提供的能力：无
- 所需能力：来自 `captive-portal` 的 `CaptivePortal`、来自 `imessage-gateway` 的
  `IMessageGateway`、来自 `webserver` 的 `WebServer`
- Workflow：无（收到的消息以 Gateway 的
  `gateway.message.received` 形式到达 Workflow）
- Agent 工具：无
- Lua 包：无
- Web：门户入口 `imessage-inkbox`，带状态；`POST
  /api/gateway/inkbox`、`GET /api/gateway/inkbox/status`、`POST
  /api/gateway/inkbox/mode`、`GET /api/gateway/inkbox/owners`、`POST
  /api/gateway/inkbox/owners`、`POST /api/gateway/inkbox/signup`、`POST
  /api/gateway/inkbox/verify`、`POST /api/gateway/inkbox/resend`（见
  [HTTP API](/zh/plugins/imessage-inkbox/http)）
- 任务：`inkbox_receive_task`（池大小 1），一个接收循环（见下文），在消息通道已配置且处于 `send_receive` 时占用 Gateway 的一个接收名额
- 存储：插件作用域的 KV：
  - `configuration`：提供方配置；
  - `mode`：消息通道模式（`ChannelMode` JSON 字符串）；
  - `owners`：授权账号（所有者名单）；
  - `cursor`：接收游标，`{"start":"<created_at>","recent":["<id>",…]}`。

Gateway 消息通道名为 `inkbox`。

存储为空时，插件在没有提供方凭据的情况下启动。它需要 `IMessageGateway`
和 `WebServer` 能力，只通过
`IMessageGateway::http()` 访问网络，暴露 `/api/gateway/inkbox` 用于运行时配置，并在已配置且不是 `disabled` 时注册消息通道 `inkbox`，因此它可以与 BlueBubbles 的 `bluebubbles` 消息通道同时启用。Inkbox 无法引用消息，所以文本和媒体上的
`reply_to` 会被忽略，而不是导致失败。被接受的配置会在启用之前持久化，并在插件注册时恢复。存储的数据格式错误会导致注册失败。`GET /api/gateway/inkbox/status` 报告是否已配置消息通道，对于自助注册，还会报告用户的地址、agent 邮箱和认领状态。见
[HTTP API](/zh/plugins/imessage-inkbox/http)。

配置是 `{"api_key","identity_id","api_base"}`，来自自助注册时还会加上
`"signup":{"human_email","email_address","claim_status"}`。它有两种写入方式：用已有的 API key 调用 `POST /api/gateway/inkbox`（没有
`signup`），或者通过 Inkbox agent 自助注册：`POST /api/gateway/inkbox/signup`
为某人的邮箱地址创建一个 agent，把返回的 agent handle 解析为其身份 UUID，用生产环境的
`api_base` 存储配置，并注册消息通道。之后 `POST /api/gateway/inkbox/verify` 和
`POST /api/gateway/inkbox/resend` 使用存储的 API key 提交或重新发送邮件中的验证码；验证成功会存储新的认领状态。插件为每个路径保留一个 `WebRouteRegistration`。注册、验证和重新发送在各自的 HTTP 请求内运行，一次一个，最多使用一个上游连接。API key 永远不会被返回或记录到日志。

Inkbox 只显示一次 API key。当注册成功但身份查询、存储或 Gateway 注册失败时，端点状态会把这次注册结果（API key、agent handle、邮箱、认领状态和已解析的身份）保留在 RAM 中，绝不写入存储，直到它被存储或插件卸载。之后针对同一邮箱的注册会从这里继续，而不会再次向上游注册；针对另一个邮箱的注册会丢弃它。

插件遵循
[`imessage-gateway`](/zh/plugins/imessage-gateway) 的消息通道接入方式：
`/api/gateway/inkbox/status`、`/api/gateway/inkbox/mode` 和
`/api/gateway/inkbox/owners` 是共享的状态、模式和所有者端点，由 Gateway 与 `/api/gateway/inkbox` 一起通过一个前缀路由提供
（`IMessageGateway::serve_channel`）；注册相关的路由是它之下的精确 WebServer 路由。授权账号只有在消息通道配置完成后才通过
`IMessageGateway::load_owners` 加载（配对码来自 Gateway 持有的平台熵源），游标则由第一个接收 session 加载。`inkbox` 消息通道恰好在已配置且模式为 `send` 或 `send_receive` 时注册到 Gateway。在出现模式之前存储的配置按 `send` 加载。没有 Inkbox 消息通道的设备以 `send_receive` 启动，在这样的设备上完成注册时，会先设置
`send_receive`，再存储注册结果。门户入口的 `GET
/portal/status` 记录映射自 Gateway 对该消息通道的 `channel_status`（“未配置”、
“已停用”、“仅发送”、“收发中”、“连接中”、“名额已满”或“连接中断”）。

## 接收

Inkbox 没有提供私有网络中的设备可以接收的长轮询、WebSocket 或推送，所以插件采用轮询。它拥有一个 Embassy 任务
`inkbox_receive_task`，在 `start` 中生成，并与插件的任务令牌竞争，运行来自 `IMessageGateway::receive_runtime` 的运行时。除非消息通道已配置且处于 `send_receive`，否则它停住而不占用名额；启用时，它租用 Gateway 的一个接收名额（`IMessageGateway::receive_control`，绝不是请求池中的连接），并用
`GatewayHttp::poll` 在其上打开一条保持活动的连接。每隔 3 秒，它在等待 `IMessageGateway::ready()` 之后发送

```
GET {api_base}/api/v1/imessage/messages?limit=50&start_datetime=<cursor>
X-API-Key: <api key>
```

列表按从新到旧排列，`start_datetime` 包含边界值。

- **游标**。`start` 是见过的最新消息的 `created_at`，以百分号编码发送。最近处理过的 32 个 id 与它一起保存，当包含边界的起点重复出现这些消息时（包括跨重连和重启），会丢弃它们。游标最多每 10 秒存储一次，第一次轮询后会立即存储。
- **第一次轮询**。没有游标时（新身份），轮询只请求一条消息，并且只记录从哪里开始，这样之前的消息不会重放给 agent。空收件箱从纪元时间开始。
- **消息**。每页按从旧到新处理。只处理 `direction` 为 `inbound` 且带文本的消息；发送者是 `remote_number`，路由是 `inkbox`/`conversation_id`，即发送路径所用的会话。所有者的消息以 Inkbox 消息 `id` 发布；新发送者发来的配对码会把对方添加为所有者，并通过正常的发送路径向该会话发送 `PAIRED_REPLY`（“Paired. You can start chatting.”）；其他人的消息都会被丢弃并计数。群组消息不会被列出（Inkbox 的 `include_groups` 保持关闭）。
- **大页面**。超过 32 KiB 的 body 会以一半的 limit 重新请求；一个间隔内的新消息超过一整页时，会跳过最旧的消息，并给出警告。
- **错误**。401 或 403 会以
  “Inkbox rejected the API key”（前面是它的中文部分）停止接收，直到配置发生变化；429 等待 `Retry-After` 秒（缺失时为 60）；其他状态码和连接失败按运行时的退避策略重试；在一次正常轮询之后断开的连接会立即重新打开。

邮件不会被轮询：注册得到的 agent 邮箱会在 Inkbox 接收邮件，但只有 iMessage 会到达 Gateway。

每个正在接收的 Inkbox 消息通道占用的内存：接收名额的静态 socket 缓冲区
（发送 1 KiB，接收 4 KiB）、租约中的一个 TLS 会话（设备上空闲时约 35 KiB；见平台清单）、一个 2 KiB 的响应头缓冲区、解析一次轮询时最多 32 KiB 的响应 body（通常是一两条消息，不到 2 KiB）、解析后的页面，以及游标（最多 32 个 id，约 2 KiB）。

## 门户页面

需要来自 `captive-portal` 的 `CaptivePortal` 和一个私有插件文件系统作用域。注册时保留一个 `WebEntryRegistration`，对应的 `WebEntry` 的 ID 为
`imessage-inkbox`，分组为 `WebGroup::Channel`，顺序为 60，标题为 `Inkbox`，带有双语摘要，图标为 `icon.png`，没有插图，模块为 `entry.js`，并带有一个
`ResourceFiles` 提供方。卸载时移除导航入口和资源提供方；不会注册额外的 HTTP 路由。

Cargo 在编译此插件之前会自动运行声明的 `build` 任务。如果只想构建它的资源，在仓库根目录运行 `cargo plugin run build --plugin imessage-inkbox`。该声明使用共享的 `tools/web/build.ts`
脚本。前端依赖以及 format/lint/check/test 命令在仓库根目录统一管理；测试放在此插件的 `resources/web/tests/` 中。
独立的浏览器模块写入此插件的 `filesystem/resources/entry.js`。通用镜像构建器只在选中此插件时才包含该目录。门户外壳中不会打包任何业务页面。共享的 UI 源码是构建期辅助工具，而不是对其他贡献者文件的运行时依赖。

页面（`resources/web/entry.ts`，基于 captive portal 的 UI 套件和 Gateway 的消息通道页面套件构建）提供两种方式。“用邮箱新建”把邮箱提交到 `POST /api/gateway/inkbox/signup`，然后把邮件中的 6 位验证码提交到 `/verify`（“重新发送”调用 `/resend`；旁边显示冷却时间），并显示已认领身份的地址；Inkbox 自己的消息显示在相关的字段上，409 `conflict` 会回到邮箱步骤。带有 `"retry": true` 的注册错误（设备保留了这次注册）会提供
“重试”，它再次提交同一个邮箱并继续这次注册，不会再发一封邮件。
“已有 API Key”把 `{api_key, identity_id, api_base}` 提交到 `POST
/api/gateway/inkbox`；表单页脚只在这种方式下显示。页面挂载时读取 `GET /api/gateway/inkbox/status`（消息通道状态加上 `signup`）：已存储的注册会从验证码步骤继续
（`claim_status` 不是 `agent_claimed`；提示中写出 `human_email` 并预填邮箱字段，没有 `human_email` 时则说明验证码已发到对方的收件箱），或者在已认领步骤显示 agent 的 `email_address`；用 key 配置的消息通道会在表单上方显示一个带有已配置卡片的“通道”行。注册、认领或保存 key 之后，页面调用 `context.refreshStatus()`。它从不读取设置或密钥。
密钥使用密码输入框，从不保存在浏览器存储中，并在成功或卸载时清空。请求在卸载时取消，且从不自动重试。HTTP API 没有身份验证或传输加密；只在可信的配置网络中使用。
