IMessage Telegram 插件把 Telegram Bot 添加为一个 iMessage Gateway 消息通道：它存储 bot 配置，通过 Bot API 发送消息，并通过长轮询接收消息。

- 插件 ID：`imessage-telegram`
- 依赖：`imessage-gateway`、`webserver`、`captive-portal`
- 设置：无
- Context 资源：无
- 提供的能力：无
- 需要的能力：来自 `captive-portal` 的 `CaptivePortal`、来自 `imessage-gateway` 的
  `IMessageGateway`
- Workflow：无（收到的消息以 Gateway 的
  `gateway.message.received` 形式到达 Workflow）
- Agent Tool：无
- Lua 包：无
- Web：门户入口 `imessage-telegram`，带状态；`POST
  /api/gateway/telegram`、`GET /api/gateway/telegram/status`、`POST
  /api/gateway/telegram/mode`、`GET /api/gateway/telegram/owners`、`POST
  /api/gateway/telegram/owners`（见 [HTTP API](/zh/plugins/imessage-telegram/http)）
- 任务：一个，`telegram_receive_task`（池大小 1），它拥有接收循环，最多占用 Gateway 的一个接收名额，并且只在消息通道已配置且处于 `send_receive` 时占用
- 存储：插件作用域的 KV：
  - `configuration`：完整的提供方配置；
  - `mode`：消息通道模式，以 JSON 字符串表示（见下文）；
  - `owners`：授权账号，一个由 `{id, label}` 组成的 JSON 数组；
  - `offset`：接收游标，即下一个 `getUpdates` offset，以十进制字符串表示。

存储为空时，插件在没有提供方凭据的情况下启动。它的构造函数不从 `PluginContext` 获取任何东西；Gateway 提供 HTTP 客户端、接收名额和平台熵源（用于绑定码）。注册时加载配置和模式，只有已配置时才加载授权账号；存储的数据格式错误会导致注册失败。第一个接收 session 读取游标。配置路径、`/mode` 和 `/owners` 是一个前缀路由（`IMessageGateway::serve_channel`）。端点见 [HTTP API](/zh/plugins/imessage-telegram/http)。

## 模式与注册

模式就是 Gateway 的 `ChannelMode`：

- `disabled`：没有 Gateway 消息通道，没有连接；
- `send`：`telegram` 消息通道注册到 Gateway，只发送；
- `send_receive`：已注册，并加上接收循环。

新配置的消息通道以 `send_receive` 开始。在出现模式之前存储的配置按 `send` 加载。`telegram` 消息通道恰好在消息通道已配置且模式不是
`disabled` 时注册到 Gateway；注册保存在端点和任务共享的消息通道状态中。

## 接收循环

`telegram_receive_task` 在 `start` 中生成一次，让接收运行时（`IMessageGateway::receive_runtime`）与它的
`PluginTaskToken` 竞争。当消息通道未配置或不处于
`send_receive` 时，运行时停住，不占用名额。否则它持有 Gateway 接收名额中的一个租约（绝不是模型调用和发送所用的共享请求池）；当所有名额都被占用时，它报告 `no_slot`，并在 `ReceiveSlots::wait_available` 报告有名额空出时立即开始。

每个 session 通过 Gateway 的轮询辅助工具（`GatewayHttp::poll`），在租约的客户端工厂上打开一条保持活动的连接，并循环执行：

1. 等待 `IMessageGateway::ready()`；
2. `GET /bot<token>/getUpdates?timeout=50&limit=8&allowed_updates=["message"]&offset=<cursor>`；
3. 收到 `ok` 回答时，报告 `receiving`，并按顺序处理每个 update。

在一次正常轮询之后断开的连接会立即重新打开；其他失败从 1 秒退避到 30 秒。

- **游标。**offset（最后的 `update_id` + 1）在下一次轮询时确认所有已处理的 update。它保存在 RAM 中，最多每 10 秒写入一次 `offset`。新的 bot token 会清除它。
- **重复。**会记住最近处理的 16 个 `update_id`；再次发送的 update（例如重连之后）会被丢弃。
- **消息。**带有发送者和 `text` 的消息，或者带有下列媒体之一的消息（其 `caption` 作为文本，可能为空），会被处理。贴纸、服务消息和其他内容会被跳过，并记录一条调试日志。
- **授权账号。**发送者是 `from.id`，标签为 `@username` 或名字。`Owners::classify` 在获取任何文件之前，根据文本或说明文字作出判断：
  - 所有者的消息作为 `GatewayInboundMessage` 发布，路由为
    `{channel: "telegram", conversation_id: <chat.id>}`，`message_id` 为
    `<message_id>`，这样回复（以及 `reply_to`）会落在同一个聊天中，其文件（见下文）作为唯一的附件；
  - 文本是绑定码或 `/start <code>` 的新发送者会成为所有者，并通过提供方普通的
    `sendMessage` 收到 `PAIRED_REPLY`；
  - 其他人的消息都会被丢弃并计数。
- **错误。**
  - 因为设置了 webhook 而返回 409：每次进入
    `send_receive`（或新配置）时调用一次 `deleteWebhook`，然后继续轮询。再次出现 409，包括来自第二个轮询方的 "terminated by other getUpdates request"，会以 Telegram 的描述报告 `error` 并退避。
  - 429：至少等待 `parameters.retry_after`。
  - 401 或 404（token 错误或已被撤销）：报告 `error` 并停止，直到配置或模式发生变化。
- **内存。**每个正在接收的消息通道：
  - 一个 1 KiB 的响应头缓冲区和一个 512 字节的读取块；
  - 解码一次轮询时最多 16 KiB 的响应 body；它直接解码到用到的少数几个字段中。超过上限的批次会改为一次一个 update 重新获取，单个 update 超过上限时会被确认并跳过，同时给出警告；
  - 租约的 TLS 会话，空闲时约 35 KiB，带有 16 KiB 输入和 4 KiB 输出的记录缓冲区；
  - 名额的静态 1 KiB 发送和 4 KiB 接收 socket 缓冲区。

截止时间：连接 30 秒，每次轮询 70 秒，`deleteWebhook` 30 秒。

## 媒体

所有者的消息最多携带一个文件，它会成为
`GatewayInboundMessage::attachments` 条目：

| 字段 | 类型 | MIME 类型 |
| --- | --- | --- |
| `photo` | `image` | `image/jpeg` |
| `voice` | `audio` | 它的 `mime_type`，否则为 `audio/ogg` |
| `audio` | `audio` | 它的 `mime_type` |
| `video` | `video` | 它的 `mime_type` |
| `video_note` | `video` | `video/mp4` |
| `animation`（Telegram 还会在它旁边设置 `document`） | `video` | 它的 `mime_type` |
| `document` | `image/jpeg`、`png`、`gif` 或 `webp` 为 `image`；否则为 `file` | 它的 `mime_type` |

没有 MIME 类型的字段交给下载的 `Content-Type` 决定。发送者的 `file_name` 就是附件的 `filename`。照片的各个尺寸中，取 `file_size` 在 Gateway 的 `attachment_max_bytes()` 以内的最大尺寸，否则取所有尺寸中最大的那个，它会被下面的大小检查拒绝。

1. `file_size` 超过 `attachment_max_bytes()` 时直接拒绝，不发请求。
2. 在共享请求池上发送 `GET <api_base>/bot<token>/getFile?file_id=<file_id>`（其回答最多读取 2 KiB），得到 `file_path`；那里的 `file_size` 超过限制时也会被拒绝。
3. `IMessageGateway::download_inbound` 把
   `<api_base>/file/bot<token>/<file_path>` 流式写入
   `/workspace/cache/gateway/telegram/`，同样在共享请求池上进行。

被拒绝、超过限制或失败（API 拒绝、非 2xx 状态、传输或存储失败）的文件不会导致消息被丢弃：会在消息文本后追加一行，`[<kind> too large, not received]` 或
`[<kind> not received]`，消息仍然会被发布。陌生人的消息和配对消息中的文件永远不会被获取。下载在处理 update 时一次进行一个，此时下一次轮询会等待；它们的缓冲区就是 Gateway 的下载缓冲区，只在下载期间占用。

发送音频（`send_media` 带 `audio`）时，如果其 MIME 类型为 `audio/ogg`，或文件名以 `.oga` 或 `.opus` 结尾，则使用 `sendVoice`（字段 `voice`，默认名称 `voice.ogg`），这样 Telegram 会显示为语音消息；其他音频通过 `sendAudio` 发送。

## 门户页面

需要来自 `captive-portal` 的 `CaptivePortal` 和一个私有插件文件系统作用域。注册时保留一个 `WebEntryRegistration`，对应的 `WebEntry` 的 ID 为
`imessage-telegram`，分组为 `WebGroup::Channel`，顺序为 20，标题为 `Telegram`，带有双语摘要，图标为 `icon.svg`，没有插图，模块为 `entry.js`，并带有一个
`ResourceFiles` 提供方。它的 `GET /portal/status` 记录是基于
`IMessageGateway::channel_status` 的 `entry_status`：“未配置”、“已停用”、“仅发送”、
“收发中”、“连接中”、“名额已满”或“连接中断”。
卸载时移除导航入口和资源提供方。

Cargo 在编译此插件之前会自动运行声明的 `build` 任务。如果只想构建它的资源，在仓库根目录运行 `cargo plugin run build --plugin imessage-telegram`。该声明使用共享的 `tools/web/build.ts`
脚本。前端依赖以及 format/lint/check/test 命令在仓库根目录统一管理；测试放在此插件的 `resources/web/tests/` 中。
独立的浏览器模块写入此插件的 `filesystem/resources/entry.js`。通用镜像构建器只在选中此插件时才包含该目录。门户外壳中不会打包任何业务页面。共享的 UI 源码是构建期辅助工具，而不是对其他贡献者文件的运行时依赖。

页面（`resources/web/entry.ts`，基于 captive portal 的 UI 套件和 Gateway 的消息通道页面套件构建）把
`{token, api_base, draft_min_delta_bytes}` 提交到 `POST /api/gateway/telegram`。它的
“验证”按钮直接从浏览器调用 Bot API 的 `getMe`（Telegram 允许任何源），使用“高级”中的 `api_base`：bot 会显示其名称、`@username` 以及
`https://t.me/<username>` 的二维码；Telegram 的 `error_code` 和
`description` 显示在 token 字段上。当浏览器无法访问外网时（连在设备热点上的手机），页面会注明 token 未经验证；验证从不阻止保存。设备的错误 `message` 显示在提示中。页面挂载时读取 `GET /api/gateway/telegram/status`，它报告消息通道状态，从不返回设置；已配置的消息通道会在替换它的表单上方显示为一个带有已配置卡片的“通道”行。保存成功后也会出现这一行，然后页面调用 `context.refreshStatus()`，让门户的导航和概览随之更新。它从不读取设置或密钥。
密钥使用密码输入框，从不保存在浏览器存储中，并在成功或卸载时清空。请求在卸载时取消，且从不自动重试。HTTP API 没有身份验证或传输加密；只在可信的配置网络中使用。
