---
title: "barracuda-e2e"
description: "针对真实的 `local-linux` System 运行端到端场景，模型调用使用回放。"
---

主机 Barracuda System 的端到端测试框架。每个场景都在一个刚擦除的 Flash 镜像上启动真实的 `local-linux` System，通过 `barracuda chat` CLI 消息通道和直接的 WebServer 请求驱动它，用一个 llm-tape 录制带响应每一次模型调用，并对回复记录、工具结果、模型可见的请求体和 System 日志进行断言。

```text
scenario.toml ──> tape (scripted or recorded) ──> llm-tape replay (0.0.0.0:18787)
                                                        ^
barracuda chat ──WebSocket──> System (10.42.0.2:8787) ──┘ model API at 10.42.0.1
      │                          │
 transcript.jsonl            system.log   ──> assertions
```

## 前提条件

```bash
cargo board select local-linux
sudo sh platforms/linux/provision.sh barracuda0
uv sync --all-packages --all-groups
```

## 运行

```bash
uv run --package barracuda-e2e barracuda-e2e list
uv run --package barracuda-e2e barracuda-e2e run                # all scenarios
uv run --package barracuda-e2e barracuda-e2e run tool-vm --skip-build
```

除非指定了 `--skip-build`，`run` 会构建 System、CLI 和插件资源镜像。场景按顺序运行，因为它们共用同一个 TUN 地址。每个场景的产物写入 `target/e2e/<name>/`：`system.log`、`llm-tape.log`、`transcript.jsonl`、`requests/`（每个模型请求体），以及隔离的 `state/` 目录。`target/e2e/summary.json` 记录每个场景的结果和普通堆的高水位。

测试框架通过一条 iptables DNAT 规则，用主机时钟响应 System 的 SNTP 请求，因此时间、Scheduler 和 Workflow 场景不依赖公共 NTP。安装这条规则需要 root 权限，测试框架不是 root 时通过 `sudo -n` 获取；没有它时，运行会打印警告，基于时间的场景可能会失败。运行结束时这条规则会被移除。传入 `--no-local-ntp` 可以改用真实的 NTP。

`--shard K/N` 从第 K 个开始，每隔 N 个运行一个选中的场景，因此 N 个并行运行恰好覆盖整个集合一次。CI 把整个集合分成四个分片运行。

## 覆盖率

```bash
rustup component add llvm-tools
uv run --package barracuda-e2e barracuda-e2e run --coverage
```

`--coverage` 还会用 LLVM 基于源码的覆盖率把 System 构建到 `target/coverage`，并运行这个构建。它的 profile 运行时持续写入计数器，因此计数器能在结束每个场景的中断之后保留下来。运行会打印每个 crate 的行覆盖率，业务代码（`plugins/`、`shared/`、`core/`）排在前面，并写入 `target/e2e/coverage/summary.json`，以及位于 `target/e2e/coverage/html/` 下的业务代码 HTML 报告。

## 场景

场景位于 `scenarios/*.toml`。

```toml
name = "Time tool"

[model]
mode = "scripted"          # scripted | recorded | none
# backend = "anthropic_compatible"  # recorded only; default openai_compatible

[[model.responses]]        # one per /chat/completions call, in order
tool_calls = [{ name = "tool_load", arguments = { group_id = "time" } }]

[[model.responses]]
tool_calls = [{ name = "time_now", arguments = {} }]

[[model.responses]]
request_contains = ['"utc"']   # the request answered here must contain this
text = "I checked the clock."

[[model.responses]]            # a model fault instead of a normal response
status = 503                   # HTTP status (default 200)
raw = '{"error":"overloaded"}' # verbatim body instead of synthesized SSE
# abort = true                 # drop the connection after the body

[[steps]]                  # one stdin line to the CLI per step
send = "What time is it?"
reply_contains = ["I checked the clock."]
reply_matches = ['clock\.$']
tool_contains = ['"utc":"20']
notice_contains = []       # CLI notices, such as a permission prompt
kinds = ["tool"]           # message roles that must appear in the turn
# request_contains = []    # recorded only: some model request of this step
# restart = true           # restart the System from its flash before this step
# tool_errors_allowed = true

[[http]]                   # direct WebServer request after startup
method = "GET"
path = "/api/wifi/status"
status = 200
body_contains = ['"station"']

[logs]
expect = ["Agent created session"]   # regexes that must appear
forbid = ['\bERROR\b']               # default: ERROR and panics
allow = []                           # exceptions to forbid
ready = ["UTC clock synchronized"]   # wait for these before the first step
await = ["VM run 1 finished"]        # wait for these after the chat
await_seconds = 30

[memory]
heap_high_water_max = 131072          # ordinary-heap budget in bytes
```

插件的 Tool 是隐藏的分组：脚本化的模型必须先 `tool_load` 该分组（`file`、`http`、`time`、`vm`、`workflow`、`scheduler`、`gateway`、`websearch`），才能调用其中的 Tool，与真实模型的做法完全一样。参数字符串可以使用 `${now}` 或 `${now+Ns}`，它们在生成录制带时被展开为 RFC3339 UTC 毫秒时间。

当 Tool 结果是 `tool not found` 或一个 `{"error": ...}` 对象、llm-tape 拒绝或错过一次模型调用，或者 System 记录了 `ERROR` 或 panic 时，每个场景也都会失败。

让脚本化场景保持在八个已提交的轮次以下，并远低于压缩阈值（大约 24 KB 的对话记录）。八个轮次之后，Agent 会提取长期记忆，较长的对话记录也会被总结；两者都会发起一次脚本化录制带无法响应的非流式模型调用，因此这次调用会拿走下一个脚本化响应，之后的每一步都会错位。后台完成（例如在其轮次结束后才结束的 VM 运行）会启动它自己的一个轮次，同样计入。把更长的用例拆分到带编号的文件中，例如 `edge-vm-output-2`。

### 虚拟 GPIO 和 I2C

每次运行都以 `BARRACUDA_VIRTUAL_IO_ADDR=127.0.0.1:18790` 启动 System，并连接到它的虚拟外设管理器（协议见[虚拟 I/O](/zh/platforms/virtual-io)）。开发板暴露 `vio-0` 到 `vio-7` 以及 I2C 控制器 `I2C0` 和 `I2C1`；第一个 `i2c.open` 得到 `I2C0`。它声明的外设位于 `I2C2` 上：位于 `0x32` 的 `real-time-clock` RX8130CE 模型和位于 `0x40` 的 `power-monitor` INA226 模型，它们在启动期间初始化。`[virtual_io]` 表在启动之后设置硬件，并在聊天之后检查硬件：

```toml
[virtual_io]
inputs = { vio-2 = true }            # externally driven input levels

[[virtual_io.devices]]               # generic 256-byte register device
address = 0x50                       # bus defaults to "I2C0"
data = "0a0b"                        # optional initial bytes from offset 0

[[virtual_io.faults]]
address = 0x51                       # omit for every address on the bus
fault = "nack"                       # nack | arbitration-loss | timeout | bus-error
once = false                         # default true: fires once

[[virtual_io.expect_pins]]           # after the chat; any of mode, level, output,
pin = "vio-0"                        # pull, drive, function, driven, claimed
mode = "output"
level = true

[[virtual_io.expect_registers]]
address = 0x50
offset = 0x10
data = "a1b2"

[[virtual_io.expect_events]]         # some recorded event has these fields;
kind = "i2c"                         # lists match by prefix
address = 0x51
result = "nack"
```

当设备模型报告违反数据手册顺序或时序的情况时，每个场景都会失败，除非设置了 `allow_violations = true`。最终的引脚、总线、事件和违规记录写入 `target/e2e/<name>/virtual-io.json`。

### 内存

主机平台把普通（内部 RAM）堆与大容量内存分开计数，后者在设备上位于 PSRAM 中。随着峰值增长，它会记录 `ordinary heap high-water: N
bytes`，每一行结果都会显示该场景的峰值。`[memory] heap_high_water_max` 会让峰值超出预算的场景失败。`run --heap-limit BYTES` 则直接限制堆本身，因此超出限制的分配会像设备内存耗尽那样中止 System。仅限主机的分配（I/O reactor、日志器和 TUN 驱动）也会被计入，因此主机上的数值是设备上数值的上限。

### scripted、recorded 和 none

- `scripted` 根据 `[[model.responses]]` 合成一个兼容 OpenAI 的流式录制带；它完全离线且是确定性的。
- `recorded` 回放 `tapes/<scenario>.jsonl`。针对真实的服务商录制或刷新它（请求体和凭据从不被存储）：

  ```bash
  uv run --package barracuda-e2e barracuda-e2e run my-scenario --record \
    --env-file /path/to/llm.env
  ```

  env 文件提供 `BARRACUDA_LLM_BASE_URL`、`BARRACUDA_LLM_API_KEY` 和 `BARRACUDA_LLM_MODEL`。回放要求 Agent 在每个对话中发起相同顺序的模型调用，因此要让录制的场景保持简短，并编写宽容的断言。来自并发对话（一个 Agent 及其子 Agent）的调用可能以任意顺序到达：新的录制带有每个对话的键，llm-tape 按它进行匹配。把录制带视为敏感数据：响应是原样存储的。
- `none` 不发起任何模型调用；把它用于只有 `[[http]]` 的场景。

对于真实模型在步骤文本的指示下能做到的一切，包括无效参数和错误路径，都使用 `recorded`。把 `scripted` 留给真实服务商无法按需产生的故障：HTTP 错误状态、被截断或中止的流、格式错误的 SSE 或工具调用 JSON，以及类似情况。脚本化响应的 `raw` 会替换合成的流，因此它可以承载上述任何一种情况；以 `data:` 开头的响应体以 `text/event-stream` 提供，其他的以 `application/json` 提供。

带有 `restart = true` 的步骤会中断 System，并从它上一次运行留下的 Flash 重新启动它，然后在一个新的聊天中发送该步骤的消息。模型 API 配置不会再次应用，因此由恢复出来的配置进行响应。

录制步骤的 `request_contains` 会对照该步骤活跃期间发出的模型请求进行检查：从请求体中带有该步骤消息的第一个请求开始，直到带有下一个步骤消息的第一个请求为止，因此这之间子 Agent 或后台轮次的请求也计入该步骤。

### 直连

`run --direct --env-file FILE` 在没有录制带的情况下运行 `recorded` 场景：System 自己通过它自己的 TLS 和信任根调用服务商，因此这是对 HTTPS 的端到端检查。不会录制任何内容，回放检查也会被跳过。

拦截 TLS 的网络（例如沙箱的出口网关）会出示它自己的 CA，System 理所当然地会拒绝它。`--test-roots PEM` 构建的主机 System 会额外信任该文件中的根证书；设备固件拒绝这个选项，构建时也会警告不要交付它：

```bash
uv run --package barracuda-e2e barracuda-e2e run live-chat --direct \
  --env-file /path/to/llm.env --test-roots /path/to/gateway-ca.pem
```

`provision.sh` 把转发连接的 TCP MSS 限制为路径 MTU：System 的 TCP 栈会忽略 ICMP“需要分片”消息，因此如果没有这个限制，当出站链路的 MTU 小于 TUN 的 MTU 时，全尺寸的报文段就会消失。
